Pruebas end-to-end con Cypress: probar el sistema como lo usa una persona

Una prueba end-to-end es un programa que usa tu aplicación por ti: abre un navegador de verdad, escribe en los campos, hace clic en los botones y después comprueba que en la pantalla apareció lo que tenía que aparecer. Si algo no calza, te avisa.

Eso es todo. El resto de este documento es aprender a escribirlas con Cypress, la herramienta que hace esa pega.

Cinco ejercicios cortos, cada uno con una sola idea, y un ejercicio integrador al final donde escribes la suite completa de la mesa de soporte. No necesitas saber nada de pruebas para partir: todo lo que hace falta está explicado acá.

Cómo se dicta esto, y qué necesitas saber para seguirlo.

Lo que hace falta: haber escrito HTML y JavaScript básico, y saber correr comandos en la terminal. Lo que no hace falta: haber escrito una prueba en tu vida. Todo lo demás está explicado en el camino, incluido el vocabulario.

La preparación deja la aplicación corriendo y Cypress abierto. Es la parte más larga y no te la puedes saltar: una prueba end-to-end sin aplicación levantada no tiene nada que visitar.

El 1 y el 2 son los cimientos: cómo trabaja Cypress por dentro y cómo se le señalan los elementos de la pantalla. Si esto no queda claro, el resto son tests que pasan hoy y se caen la próxima semana.

Del 3 al 5 vamos sumando: manejar la pantalla y comprobar, controlar lo que llega del servidor, y no repetir código. El integrador junta todo en una suite real.

Punto de partida: qué es «probar» un programa

Cuando terminas una pantalla, la abres en el navegador y la usas para ver si anda: escribes tu correo, haces clic en «Entrar», miras si entraste. Eso es una prueba manual. Sirve, pero tiene tres problemas grandes:

  1. Es lenta. Revisar diez pantallas a mano se demora media hora, todos los días.
  2. Es olvidadiza. A nadie se le ocurre probar de nuevo el login cuando el cambio fue en otra parte — y ahí es justo donde se echa a perder.
  3. No deja rastro. Si mañana otra persona mete mano en el código, no tiene cómo saber qué comprobaste tú.

Una prueba automatizada es esa misma revisión, pero escrita como código que corre solo. Se ejecuta en segundos, se ejecuta siempre completa, y queda escrita para todo el equipo. No reemplaza tu criterio: lo guarda.

Todas las pruebas automatizadas tienen la misma forma.

Pase lo que pase y con la herramienta que sea, siempre son tres momentos: preparo una situación, ejecuto una acción, comparo el resultado con lo que esperaba. Si coincide, el test pasa (verde). Si no, falla (rojo) y te dice qué esperaba y qué encontró.

Puedes tener el formulario perfecto, el servicio perfecto y las rutas perfectas —cada pieza probada por separado y en verde— y que al juntarlas el botón «Entrar» no lleve a ninguna parte. Nadie probó la unión. Eso es justo lo que pilla una prueba end-to-end.

Petición HTTP: cada vez que tu página le pide datos al servidor («dame los tickets») viaja un mensaje por la red. Eso es una petición, y la contestación es la respuesta. La respuesta trae un código de estado: un número que resume cómo fue. 200 = todo bien, 401 = no estás autorizado, 500 = el servidor se cayó.

Cypress y Nightwatch hacen lo mismo. ¿Por qué elegimos Cypress?

Los dos son runners: programas que manejan un navegador siguiendo instrucciones. Nightwatch lo hace desde afuera, dándole órdenes al navegador a través de un intermediario llamado Selenium — que además exige tener Java instalado. Son dos piezas más que configurar y que se pueden romper.

Cypress corre dentro del navegador, junto a tu aplicación. Se instala con un solo comando, trae su propia ventana con la lista de pasos, y cuando algo falla te deja devolverte y ver cómo estaba la página en cada instante. Para aprender, la diferencia es enorme.

Nightwatch sigue siendo válido — en el cierre está la comparación completa — pero hoy escribimos Cypress.

Preparación — la app bajo prueba y Cypress corriendo

Objetivo: una aplicación real levantada en localhost y el primer test E2E en verde dentro del navegador. · 30 minutos.

Lo primero que hay que entender: Cypress no arranca tu aplicación

Cypress hace lo mismo que harías tú si probaras a mano: abre un navegador y escribe una dirección. Nada más. Eso significa que la aplicación tiene que estar ya funcionando en esa dirección antes de que Cypress llegue — igual que tú no puedes visitar una tienda que todavía no abrió.

Por eso hoy vas a trabajar con dos terminales abiertas al mismo tiempo: una tiene la aplicación corriendo y no se cierra nunca; la otra es donde lanzas los tests.

npm run dev→ Vite sirve la app en :5173→ cypress open→ Chrome visita la URL→ los comandos manejan la interfaz
El error número uno del primer día.

cy.visit('/') falla con «We attempted to make an http request to this URL but we received an error». Casi siempre significa lo mismo: se te olvidó levantar npm run dev en otra terminal. Cypress no te levanta la aplicación; solo la visita.

La aplicación que vamos a probar

Una mesa de soporte: la pantalla donde un agente atiende los reclamos de los clientes. Cada reclamo es un ticket. Tiene dos pantallas y nada más:

  • Login — correo y clave para entrar.
  • Cola de tickets — la lista de reclamos abiertos, con un buscador y un botón «Resolver» en cada fila.
Este código no lo tienes que entender línea por línea.

La aplicación es material entregado: cópiala tal cual y sigue. Hoy no aprendemos a construir aplicaciones, aprendemos a probarlas. De cada archivo te digo qué hace y qué parte nos importa para testear — eso es lo que sí necesitas.

Lo único que tienes que mirar con atención son los atributos data-cy="algo" que verás repartidos por las pantallas. Ésos son las manillas por donde los tests van a agarrar cada elemento, y el ejercicio 2 está dedicado entero a ellos.

Un servidor de datos para la clase

En una aplicación real, la lista de tickets no está escrita en el código: se la pide a un servidor, que es otro programa —normalmente en otra máquina— que guarda los datos y los entrega cuando se los piden. A ese programa se le llama el backend.

Montar un backend de verdad se nos come la clase entera. Así que le pedimos a Vite —el programa que ya está sirviendo nuestra aplicación— que además responda unas pocas direcciones que empiecen con /api. Son treinta líneas y guardan los tickets en memoria: cuando apagas el servidor, se olvida todo. Para aprender, sobra.

DirecciónQué haceDevuelve
POST /api/loginComprueba correo y claveLos datos del usuario, o error 401
GET /api/ticketsEntrega la lista de tickets abiertosUn arreglo con 3 tickets
POST /api/tickets/T-101/resolverMarca ese ticket como resuelto y lo saca de la lista{ ok: true }
POST /api/resetDevuelve los datos a como estaban al empezar{ ok: true }
GET y POST son los dos verbos que vas a ver hoy.

Cuando la página pide información sin cambiar nada, usa GET («dame los tickets»). Cuando manda algo que modifica el sistema, usa POST («resuelve este ticket», «entra con estas credenciales»). Es la misma diferencia que entre mirar una vitrina y comprar.

vite.config.js 
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

// ── API DE CLASE ──────────────────────────────────────────────────
// Un backend en memoria para que la app tenga datos reales al correr
// `npm run dev`. En un proyecto de verdad esto sería otro servicio;
// acá nos ahorra levantar un segundo proceso.
const SEMILLA = () => ([
  { id: 'T-101', titulo: 'No puedo iniciar sesion',  prioridad: 'alta',    minutosAbierto: 320 },
  { id: 'T-102', titulo: 'La boleta llega sin IVA',  prioridad: 'media',   minutosAbierto: 95  },
  { id: 'T-103', titulo: 'Caida total del portal',   prioridad: 'critica', minutosAbierto: 12  }
])

function apiDeClase() {
  let tickets = SEMILLA()

  const leerCuerpo = (req) => new Promise((listo) => {
    let crudo = ''
    req.on('data', (trozo) => { crudo += trozo })
    req.on('end', () => listo(crudo ? JSON.parse(crudo) : {}))
  })

  return {
    name: 'api-de-clase',
    configureServer(server) {
      // Al montar el middleware en '/api', el prefijo se recorta:
      // /api/tickets llega acá como /tickets.
      server.middlewares.use('/api', async (req, res, next) => {
        const ruta = req.url.split('?')[0]
        res.setHeader('Content-Type', 'application/json')

        if (req.method === 'POST' && ruta === '/login') {
          const { email, clave } = await leerCuerpo(req)
          const ok = email === 'soporte@demo.cl' && clave === 'clave123'
          res.statusCode = ok ? 200 : 401
          return res.end(JSON.stringify(
            ok ? { token: 'token-de-clase', nombre: 'Equipo Soporte' }
               : { mensaje: 'Correo o clave incorrectos' }
          ))
        }

        if (req.method === 'GET' && ruta === '/tickets') {
          return res.end(JSON.stringify(tickets))
        }

        if (req.method === 'POST' && /^\/tickets\/[^/]+\/resolver$/.test(ruta)) {
          const id = ruta.split('/')[2]
          tickets = tickets.filter((t) => t.id !== id)
          return res.end(JSON.stringify({ ok: true }))
        }

        // Deja los datos como recién instalados. Los tests lo llaman
        // antes de cada escenario para no depender del anterior.
        if (req.method === 'POST' && ruta === '/reset') {
          tickets = SEMILLA()
          return res.end(JSON.stringify({ ok: true }))
        }

        next()
      })
    }
  }
}

export default defineConfig({
  plugins: [vue(), apiDeClase()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) }
  },
  // Puerto fijo: si Vite se cambia solo al 5174, la baseUrl de Cypress
  // deja de apuntar a ninguna parte y todos los tests fallan igual.
  server: { port: 5173, strictPort: true }
})
Esa dirección /reset no es un capricho.

Es la respuesta a la pregunta más importante de las pruebas end-to-end: ¿cómo me aseguro de que cada escenario parta desde el mismo punto?

Piénsalo: el segundo escenario resuelve el ticket T-101. El tercero cuenta los tickets y espera tres… pero quedan dos, porque el anterior se llevó uno. El tercero se cae sin tener nada malo. Llamar a /api/reset antes de cada escenario es lo que evita esa cadena de fallos falsos. En un proyecto real esto se hace recargando la base de datos con datos de prueba; la idea es exactamente la misma.

Las piezas de la aplicación

Los siete archivos que siguen son la aplicación. Cópialos tal cual. Antes de cada uno va una línea diciendo qué hace; con eso basta para lo de hoy.

Le pide datos al servidor. Las tres funciones que la aplicación usa para hablar con el backend. fetch es la orden del navegador para mandar una petición por la red; await significa «espera a que llegue la respuesta antes de seguir».

src/servicios/api.js 
// UNA sola puerta de salida al backend. Que todo pase por acá es lo
// que después hace trivial interceptar la red desde un test.
const BASE = '/api'

export async function iniciarSesion(email, clave) {
  const respuesta = await fetch(`${BASE}/login`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ email, clave })
  })
  const datos = await respuesta.json()
  if (!respuesta.ok) throw new Error(datos.mensaje || 'No pudimos iniciar sesion')
  return datos
}

export async function obtenerTickets() {
  const respuesta = await fetch(`${BASE}/tickets`)
  if (!respuesta.ok) throw new Error('No pudimos cargar la cola')
  return respuesta.json()
}

export async function resolverTicket(id) {
  const respuesta = await fetch(`${BASE}/tickets/${id}/resolver`, { method: 'POST' })
  if (!respuesta.ok) throw new Error('No pudimos resolver el ticket')
  return respuesta.json()
}

Recuerda quién entró. localStorage es una libretita que el navegador guarda por cada sitio web y que sobrevive aunque cierres la pestaña. Ahí anotamos el usuario para no pedirle la clave en cada pantalla.

src/sesion.js 
import { ref } from 'vue'

// La sesión vive en localStorage para que sobreviva a un F5.
// Detalle importante para hoy: cy.session() sabe guardar y restaurar
// exactamente esto, y por eso podremos saltarnos el login por interfaz.
export const usuario = ref(JSON.parse(localStorage.getItem('sesion') || 'null'))

export function guardarSesion(datos) {
  usuario.value = datos
  localStorage.setItem('sesion', JSON.stringify(datos))
}

export function cerrarSesion() {
  usuario.value = null
  localStorage.removeItem('sesion')
}

Decide qué pantalla se ve según la dirección. /login muestra el formulario, /cola muestra la lista. Y al final hay un guardia: una función que se ejecuta antes de cada cambio de pantalla y devuelve al login a quien no tenga sesión. Esa regla es uno de los escenarios que vas a probar.

src/router.js

  history: createWebHistory(),

    { path: '/',      redirect: '/cola' },

})

// Guardia de navegación: /cola exige sesión. Éste es justamente el
// tipo de regla que una prueba unitaria no alcanza a ver.
router.beforeEach((destino) => {
  if (destino.meta.privada && !usuario.value) return { name: 'login' }
})

<script setup>
import { ref } from 'vue'
import { useRouter } from 'vue-router'
import { iniciarSesion } from '@/servicios/api.js'
import { guardarSesion } from '@/sesion.js'

const email = ref('')
const clave = ref('')
const error = ref('')
const enviando = ref(false)

async function enviar() {
  error.value = ''
  enviando.value = true
  try {
    guardarSesion(await iniciarSesion(email.value, clave.value))
    router.push('/cola')
  } catch (e) {
    error.value = e.message
  } finally {
    enviando.value = false
  }
}

Anatomía de un test E2E — y la cadena de comandos

Objetivo: entender cómo se ejecuta realmente un test de Cypress. Es el concepto que decide si el resto de la sesión te cuadra o te confunde. · 30 minutos.

La estructura de un archivo de tests

Ya viste describe e it en el test de humo. Falta la tercera pieza: beforeEach, que significa literalmente «antes de cada uno». Todo lo que pongas ahí dentro se ejecuta una vez antes de cada it del grupo, automáticamente.

Sirve para lo mismo que ordenar la mesa antes de cada cliente: ahí va la preparación que todos los escenarios necesitan, para no repetirla ni olvidarla.

Estas tres palabras no las inventó Cypress.

describe, it y beforeEach vienen de Mocha, una herramienta de pruebas para JavaScript que Cypress trae adentro. Las vas a encontrar iguales en Jest, en Vitest y en casi cualquier otra: es vocabulario compartido de la industria. Y no hay que importarlas — están disponibles solas en cualquier archivo .cy.js.

cypress/e2e/01-anatomia.cy.js 
describe('Cola de tickets', () => {
  beforeEach(() => {
    // Estado conocido antes de CADA escenario. Sin esto, el test que
    // resuelve un ticket rompe al siguiente. Es la regla de las pruebas
    // que la leccion llama "aisladas": no dependen del orden.
    cy.request('POST', '/api/reset')
    cy.visit('/login')
  })

  it('muestra el formulario de acceso', () => {
    cy.get('[data-cy="form-login"]').should('be.visible')
    cy.get('[data-cy="entrar"]').should('contain', 'Entrar')
  })
})
Dado→ visito /login sin sesión· Cuando→ escribo credenciales válidas y envío· Entonces→ llego a /cola y veo mis tickets
Todo escenario tiene esos tres momentos. Escríbelos siempre en ese orden.

Dado = la situación de partida (va casi siempre en el beforeEach). Cuando = la acción del usuario, y es una sola. Entonces = las comprobaciones.

En inglés lo vas a leer como Given / When / Then, y en pruebas unitarias como Arrange / Act / Assert — «preparar, ejecutar, comprobar». Son tres nombres para la misma idea; no te compliques con cuál usar.

El concepto que hay que entender hoy: los comandos se encolan

Esto le complica la vida a todo el mundo la primera semana, así que vamos despacito.

Cuando lees código normal, cada línea se ejecuta y termina antes de que empiece la siguiente. Cypress no anda así. Cuando escribes cy.get(...), en ese instante no pasa nada: Cypress solo anota el encargo en una lista y sigue leyendo. Recién cuando terminó de leer todo el it, empieza a ejecutar la lista de arriba abajo, esperando que cada encargo termine antes de pasar al siguiente.

Cypress lee tu it completo→ anota los encargos en una lista→ recién ahí→ los ejecuta uno por uno, esperando cada vez

¿Por qué importa? Porque tiene una consecuencia práctica enorme: como en el momento de escribir la línea todavía no se ejecutó nada, cy.get(...) no te puede devolver el elemento. Todavía no existe. Por eso guardarlo en una variable no sirve de nada.

Lo que mucha gente escribe 
it('cuenta los tickets', () => {
  // cy.get NO devuelve el elemento.
  // Devuelve la propia cadena de Cypress.
  const lista = cy.get('[data-cy="lista"]')

  // Esto es undefined: no existe .length
  console.log(lista.length)

  // Y esto tampoco funciona:
  const cuantos = cy.get('[data-cy="ticket"]').length
  expect(cuantos).to.equal(3)
})
Lo que hay que escribir 
it('cuenta los tickets', () => {
  // La afirmacion va DENTRO de la cadena.
  // Cypress reintenta hasta que se cumpla.
  cy.get('[data-cy="ticket"]').should('have.length', 3)

  // Si de verdad necesitas el valor en JS,
  // se entra con .then():
  cy.get('[data-cy="ticket"]').then((elementos) => {
    expect(elementos.length).to.equal(3)
  })
})
No pongas await delante de un comando de Cypress.

Si ya escribiste JavaScript que habla con un servidor, conoces await: la palabra que significa «detente acá hasta que esto termine». Con Cypress no se usa. Sus comandos no son de los que await sabe esperar, así que await cy.get(...) no espera nada útil y encima desordena la lista de encargos.

La regla es simple: en un archivo .cy.js no se escribe await nunca. Cypress ya espera solo, y eso es justamente lo que viene ahora.

El reintento automático: por qué casi nunca vas a esperar a mano

Cuando haces clic en «Entrar», la pantalla no cambia al instante: hay que mandar la petición al servidor, esperar la respuesta y volver a dibujar la lista. Puede tomar 40 milisegundos o dos segundos, y tú no sabes cuánto.

Cypress resuelve esto solo. Cuando una orden de buscar —cy.get, cy.contains— va seguida de un .should(...), Cypress vuelve a mirar la página una y otra vez hasta que la comprobación se cumple, o hasta que pasan 4 segundos y se rinde. No tienes que andar diciéndole cuánto esperar: espera lo justo.

Ésta es la mejor característica de Cypress y la razón de la mitad de sus reglas raras.

Es también el motivo de que no se use await: la espera ya está adentro del par buscar + comprobar.

cypress/e2e/01-anatomia.cy.js 
it('la cola carga sola, sin esperas manuales', () => {
  cy.get('[data-cy="email"]').type('soporte@demo.cl')
  cy.get('[data-cy="clave"]').type('clave123')
  cy.get('[data-cy="entrar"]').click()

  // Entre el click y esta linea pasan cuatro cosas: cambia la
  // pantalla, sale la peticion, llega la respuesta y se dibuja la
  // lista. No escribimos ni una espera: Cypress mira una y otra vez
  // hasta que hay 3 tickets, o se rinde a los 4 segundos.
  cy.get('[data-cy="ticket"]').should('have.length', 3)
})

Ahora bien, no todas las órdenes se reintentan, y saber cuáles sí evita harta confusión. La división es sencilla: las que miran se repiten, las que hacen no.

Órdenes que MIRAN — sí reintentanÓrdenes que HACEN — no reintentan
Cuáles son cy.get(), cy.contains(), .find(), .its() .click(), .type(), cy.visit()
Qué hacen Buscan algo en la página sin modificarla Cambian algo: escriben, aprietan, navegan
Comportamiento Se repiten hasta que la comprobación de al lado se cumple Se ejecutan una vez; si el elemento no está, el test falla ahí mismo
Por qué Mirar dos veces no hace daño Repetir un clic sí: comprarías dos veces
Un detalle fino que explica un error que vas a ver.

Cuando encadenas varias búsquedas, Cypress solo repite la última. En cy.get('ul').find('li').should('have.length', 3) vuelve a intentar el .find('li'), pero se queda con el <ul> que encontró la primera vez. Si mientras tanto la aplicación reemplazó esa lista entera por una nueva, Cypress se queda agarrado de una lista que ya no está en la página y verás el mensaje «element is detached from the DOM» — «el elemento se soltó de la página».

La solución: en vez de encadenar dos búsquedas, haz una sola que apunte directo a lo que te interesa — cy.get('[data-cy="ticket"]').

Un buen test E2E se lee como el guion de una persona usando la aplicación. Si para entenderlo hay que abrir el código de la aplicación, está mal escrito.

Selectores — por qué data-cy y no una clase CSS

Objetivo: elegir selectores que sobrevivan al próximo rediseño. Es el 80% de los tests E2E frágiles. · 20 minutos.

El problema, con nombre y apellido

Un test E2E no falla porque tu lógica esté mal. Falla porque alguien le cambió la clase a un botón, o metió un <div> nuevo y el :nth-child(2) ahora apunta a otra cosa. A eso se le llama test frágil: se rompe con cambios que no rompieron nada.

Selectores frágiles 
it('resuelve el primer ticket', () => {
  // Atado al diseño: cambia el CSS y esto muere
  cy.get('.btn.btn-primary.rounded').click()

  // Atado al orden del DOM: agrega un div arriba
  // y apunta a otro elemento
  cy.get('main > div:nth-child(2) > ul > li')
    .first()
    .find('button')
    .click()

  // Atado a un id de framework: cambia en cada build
  cy.get('#app_input_42').type('portal')
})
Selectores estables 
it('resuelve el primer ticket', () => {
  // Atado a NADA visual. Solo se rompe si alguien
  // borra el atributo a proposito.
  cy.get('[data-cy="ticket"]')
    .first()
    .find('[data-cy="resolver"]')
    .click()

  cy.get('[data-cy="filtro"]').type('portal')

¿Y qué es exactamente un data-cy?

Un atributo que te inventas tú. HTML permite agregarle a cualquier etiqueta atributos propios siempre que empiecen con data-. El navegador los ignora por completo: no cambian cómo se ve ni cómo funciona nada. Están ahí solo para que alguien los lea, y ese alguien es tu test.

Por eso es el selector más estable que existe: nadie lo va a tocar por motivos de diseño, porque no hace nada visual. Y cuando otra persona ve data-cy="resolver" en el HTML entiende al tiro dos cosas: que hay un test apoyado ahí, y que si lo borra lo rompe. Una clase CSS no comunica nada de eso — parece decoración, y se cambia sin avisar.

Cuándo sí conviene buscar por texto

cy.contains() no es el enemigo. Cuando el texto es lo que se le prometió al usuario —el mensaje de error, el título de la página, la etiqueta del botón principal— afirmar sobre él tiene todo el sentido: si cambia, cambió el producto.

// Bien: el texto es el comportamiento que estoy verificando
cy.contains('h1', 'Cola de tickets').should('be.visible')
cy.contains('[data-cy="error-login"]', 'Correo o clave incorrectos')

// Bien: acota la busqueda a un contenedor identificado
cy.get('[data-cy="lista"]').contains('Caida total del portal')

// Mal: 'Resolver' aparece 3 veces en la pagina.
// Cypress toma el primero y el test miente.

cy.contains() devuelve el PRIMER elemento que coincide, no todos. Si el texto se repite —y en una lista siempre se repite— vas a estar probando la primera fila creyendo que estás probando cualquiera. Acota siempre con un contenedor: cy.get('[data-cy="ticket"]').eq(1).contains('Resolver').

Recorrer una lista sin depender de posiciones

Nuestros <li> llevan data-cy="ticket" y también :data-id="t.id". Ese segundo atributo es el que permite apuntar a un ticket concreto sin contar filas.

cypress/e2e/02-selectores.cy.js 
describe('Seleccion dentro de la lista', () => {
  beforeEach(() => {
    cy.request('POST', '/api/reset')
    cy.visit('/login')
    cy.get('[data-cy="email"]').type('soporte@demo.cl')
    cy.get('[data-cy="clave"]').type('clave123')
    cy.get('[data-cy="entrar"]').click()
  })

  it('encuentra un ticket por su identificador, no por su posicion', () => {
    cy.get('[data-cy="ticket"][data-id="T-102"]')
      .should('contain', 'La boleta llega sin IVA')
      .find('[data-cy="prioridad"]')
      .should('have.text', 'media')
  })

  it('afirma sobre TODOS los elementos de la lista', () => {
    // .each recorre la coleccion completa.
    // Si mañana llegan 40 tickets, el test sigue sirviendo.
    cy.get('[data-cy="ticket"]').each((fila) => {
      cy.wrap(fila).find('[data-cy="titulo"]').should('not.be.empty')
      cy.wrap(fila).find('[data-cy="resolver"]').should('be.enabled')
    })
  })
})
Qué son .each() y cy.wrap(), sin misterio.

.each() significa «para cada uno». Recorre todos los elementos que encontraste y ejecuta el mismo bloque con cada uno, uno por uno. La variable fila es el elemento del turno actual.

Ahora, ese fila llega como un elemento «pelado», sin los poderes de Cypress: no espera, no reintenta y no aparece en el panel de la interfaz. cy.wrap(fila) se lo devuelve — literalmente «envuélvemelo». La regla práctica: dentro de un .each(), envuelve siempre antes de seguir encadenando.

Red y esperas — cy.intercept y el fin de cy.wait(3000)

Objetivo: esperar por hechos, no por tiempo, y forzar estados del sistema que a mano son imposibles de reproducir. · 35 minutos.

El pecado capital del testing E2E

La espera ciega 
cy.get('[data-cy="entrar"]').click()

// "Le doy 3 segundos, deberia alcanzar"
cy.wait(3000)

cy.get('[data-cy="ticket"]').should('have.length', 3)
La espera por un hecho 
cy.intercept('GET', '/api/tickets').as('cargarCola')

cy.get('[data-cy="entrar"]').click()

// Espero a que ESA peticion termine. Ni un ms mas.
cy.wait('@cargarCola')

cy.get('[data-cy="ticket"]').should('have.length', 3)
cy.wait(3000) es malo por los dos lados.

En tu computador son 3 segundos regalados en cada test; multiplícalo por 40 escenarios y tu suite se demora dos minutos más de lo necesario. Y en el servidor de CI, que anda harto más lento, 3 segundos no alcanzan y el test falla sin motivo real. Eso es un test flaky: el que a veces pasa y a veces no. Un test flaky es peor que no tener test, porque enseña al equipo a ignorar el rojo.

cy.intercept: ponerse en el medio de la conversación

Tu aplicación y el servidor conversan por la red: la página pide («dame los tickets») y el servidor contesta. cy.intercept pone a Cypress en el medio de esa conversación, como quien escucha una llamada por el otro auricular.

Y una vez ahí, puede hacer tres cosas distintas:

tu página pide→ Cypress escucha→ deja pasar · o contesta él mismo · o finge un error→ tu página recibe
  1. Escuchar y dejar pasar. La petición llega al servidor normalmente, pero ahora Cypress sabe cuándo terminó — y por eso puede esperarla.
  2. Contestar él mismo. La petición no sale nunca: Cypress devuelve los datos que tú le dictaste. Así montas cualquier situación que se te ocurra.
  3. Fingir que salió mal. Contesta con un error, o contesta lento a propósito.
Lo que quieresCómo se escribe¿Llega al servidor?
Espiar y poder esperarcy.intercept('GET', '/api/tickets').as('cola')Sí, pasa de largo
Responder con datos fijoscy.intercept('GET', '/api/tickets', { body: [...] })No
Responder desde un archivocy.intercept(..., { fixture: 'cola.json' })No
Forzar un errorcy.intercept(..., { statusCode: 500 })No
Simular lentitudcy.intercept(..., { delay: 1500, body: [] })No
Dos palabras que vas a escuchar toda tu carrera.

A la pieza que solo observa sin cambiar nada se le llama spy (espía) — es un cy.intercept sin respuesta. A la que fija lo que se devuelve, para forzar una situación, se le llama stub — es un cy.intercept con respuesta.

No es vocabulario de Cypress: es de las pruebas en general, y lo vas a encontrar en cualquier herramienta y en cualquier lenguaje. Guárdate la diferencia: espía = mira; stub = responde.

La palabra alias, que aparece en todos los ejemplos

Cuando escribes .as('cargarCola') al final de un cy.intercept, le estás poniendo un apodo a esa petición. Después te refieres a ella con '@cargarCola' — la arroba significa «el apodo que puse antes».

Sirve para eso exactamente: para poder decir cy.wait('@cargarCola'), o sea, «espera a que esa petición en particular termine». El nombre lo eliges tú y no tiene ninguna magia; solo tiene que coincidir en los dos lados.

El orden importa: interceptar ANTES de provocar la petición

cypress/e2e/04-red.cy.js 
describe('La cola frente a la red', () => {
  beforeEach(() => {
    cy.request('POST', '/api/reset')
  })

  it('espera a que la cola termine de cargar', () => {
    // 1. Primero declaro la intercepcion...
    cy.intercept('GET', '/api/tickets').as('cargarCola')

    // 2. ...y RECIEN despues navego.
    // Al reves, la peticion ya salio y nadie la escucho.
    cy.visit('/login')
    cy.get('[data-cy="email"]').type('soporte@demo.cl')
    cy.get('[data-cy="clave"]').type('clave123{enter}')

    cy.wait('@cargarCola').its('response.statusCode').should('eq', 200)
    cy.get('[data-cy="ticket"]').should('have.length', 3)
  })
})
Si intercepta después, no intercepta nada.

cy.intercept instala un oyente. Una petición que salió antes de que el oyente existiera es una petición que Cypress nunca pilló, y tu cy.wait('@alias') se va a quedar esperando hasta el timeout con el mensaje «no request ever occurred».

Afirmar sobre lo que se envió, no solo sobre lo que se recibió

A veces el problema no está en lo que llega, sino en lo que tu página mandó: escribiste password donde el servidor esperaba clave, o mandaste el correo con un espacio al final. Desde afuera todo parece un login que «no anda» y nadie entiende por qué.

El login por interfaz igual hay que probarlo — una vez.

Usar cy.session en todos lados no significa dejar de probar el formulario. El archivo 03-login.cy.js lo prueba a mano y en serio: feliz, inválido, protegido, con Enter. Los demás archivos no vuelven a probarlo; solo necesitan estar dentro. Probar el login veinte veces no lo prueba mejor: solo hace la suite más lenta.

Una recomendación por si buscas ejemplos en internet

Vas a encontrar tutoriales que arman una clase PaginaLogin con un método por cada campo de la pantalla. A ese patrón se le llama Page Object y viene de herramientas más antiguas. Cypress recomienda no usarlo: prefiere comandos propios como los que acabas de escribir, porque son más simples, aparecen en el panel de la ventana de Cypress y no obligan a aprender una capa extra.

No es que esté prohibido. Es que en Cypress no hace falta, y para partir solo te complica la vida.

La regla para saber si un comando propio vale la pena.

Si esconde una intención del usuario («entrar», «resolver el ticket X», «filtrar por»), hazlo. Si solo esconde un selector (cy.botonEntrar()), no: estás inventando un diccionario que nadie va a recordar y que tapa lo que el test realmente hace.

Escríbelo tú

  1. Crea el comando cy.resolverTicket(id) que busque el ticket por data-id y haga clic en su botón. Úsalo en el test de resolver.
  2. Agrega a entrar() un tercer parámetro opcional para saltarse la aserción de URL, de modo que también sirva para probar el login fallido. ¿Te gustó el resultado, o ensució el comando? Argumenta.
  3. Corre la suite con cy:open y mira el panel: cuando cy.session restaura en vez de crear, aparece marcado. Cronometra la diferencia.

Antes de seguir

  • Tienes cy.entrar(), cy.porDato() y cy.reiniciarDatos() funcionando.
  • cy.session está en uso y recuerdas el cy.visit() posterior.
  • El login por interfaz sigue probado a fondo en un solo archivo.
  • Tus tests se leen sin tener que saltar líneas de preparación.

Ejercicio integrador — La suite E2E de la mesa de soporte

Objetivo: escribir tú la suite completa, con todo lo de la sesión. · 60 minutos · Trabaja primero solo; la solución de referencia está más abajo.

El encargo

La mesa de soporte se publica el lunes: deja de ser un proyecto en tu computador y pasa a usarla gente de verdad. Tu pega es entregar la suite de pruebas end-to-end que el equipo va a correr cada vez que publique una versión nueva.

No tiene que probarlo todo. Son los trámites que, si se rompen, no se puede publicar — y nada más.

Trabajas sobre el proyecto que armamos en la preparación. Todo lo que necesitas ya existe: la app, la API de clase, Cypress configurado y tus comandos propios.

Cómo abordarlo.

Escribe un escenario a la vez y déjalo verde antes de pasar al siguiente. No escribas los nueve y después los arregles todos juntos: cuando algo falle no vas a saber si es tu test o la app.

Las reglas del entregable

  1. Todos los selectores por data-cy. Cero clases CSS, cero nth-child.
  2. Ni un solo cy.wait(número). Si necesitas esperar, intercepta y espera el alias.
  3. Cada escenario parte de un estado conocido: cy.reiniciarDatos() en el beforeEach.
  4. El login por interfaz se prueba en su propio describe; el resto usa cy.entrar().
  5. Los nombres de los it describen comportamiento de negocio, no comandos. «resuelve un ticket y no vuelve al recargar», no «test 7».
  6. La suite completa pasa con npm run cy:run, sin abrir la interfaz.
Pistas para los dos escenarios que cuestan.

El 7 necesita que confirmes que el POST llegó al servidor antes de recargar; si recargas demasiado pronto, la petición todavía va en camino. Intercepta 'POST', '/api/tickets/*/resolver' y espera el alias.

    cy.visit('/login')

      .should('be.visible')
      .and('contain', 'Correo o clave incorrectos')

    cy.url().should('include', '/login')
    cy.porDato('form-login').should('be.visible')
  })

describe('Cola de tickets', () => {
  beforeEach(() => {
    cy.reiniciarDatos()
    cy.entrar()
    cy.visit('/cola')   // imprescindible despues de cy.session
  })

  // ── 4 ────────────────────────────────────────────────────────────
  it('cada ticket muestra su titulo, su prioridad y su accion', () => {
    cy.porDato('ticket').should('have.length', 3)

    cy.porDato('ticket').each((fila) => {
      cy.wrap(fila).find('[data-cy="titulo"]').should('not.be.empty')
      cy.wrap(fila).find('[data-cy="prioridad"]').should('not.be.empty')
      cy.wrap(fila).find('[data-cy="resolver"]').should('be.enabled')
    })
  })

  // ── 5 ────────────────────────────────────────────────────────────
  it('el filtro deja solo los tickets que coinciden', () => {
    cy.porDato('filtro').type('boleta')

    cy.porDato('ticket').should('have.length', 1)
    cy.porDato('ticket').should('contain', 'La boleta llega sin IVA')
  })

  // ── 6 ────────────────────────────────────────────────────────────
  it('un filtro sin coincidencias muestra el estado vacio, no una pagina en blanco', () => {
    cy.porDato('filtro').type('cualquiercosa')

    cy.porDato('ticket').should('not.exist')
    cy.porDato('vacio').should('be.visible').and('contain', 'No hay tickets')
  })

  // ── 7 ────────────────────────────────────────────────────────────
  it('resuelve un ticket y no vuelve a aparecer al recargar', () => {
    cy.intercept('POST', '/api/tickets/*/resolver').as('resolver')

    cy.resolverTicket('T-101')

    // Confirmo que el servidor recibio la orden antes de recargar
    cy.wait('@resolver').its('response.statusCode').should('eq', 200)

    cy.get('[data-cy="ticket"][data-id="T-101"]').should('not.exist')
    cy.porDato('ticket').should('have.length', 2)

    // La prueba de fuego: recargo desde el servidor
    cy.visit('/cola')
    cy.get('[data-cy="ticket"][data-id="T-101"]').should('not.exist')
    cy.porDato('ticket').should('have.length', 2)
  })

  // ── 8 ────────────────────────────────────────────────────────────
  it('al resolver toda la cola muestra el estado vacio', () => {
    cy.intercept('POST', '/api/tickets/*/resolver').as('resolver')

    cy.resolverTicket('T-101')
    cy.wait('@resolver')
    cy.resolverTicket('T-102')
    cy.wait('@resolver')
    cy.resolverTicket('T-103')
    cy.wait('@resolver')

    cy.porDato('ticket').should('not.exist')
    cy.porDato('vacio').should('be.visible')
  })
})


describe('La cola cuando la API falla', () => {
  beforeEach(() => {
    cy.reiniciarDatos()
    cy.entrar()
  })

  // ── 9 ────────────────────────────────────────────────────────────
  it('muestra un mensaje humano y se recupera al reintentar', () => {
    // Primera respuesta: el servidor se cae
    cy.intercept('GET', '/api/tickets', { statusCode: 500 }).as('colaRota')
    cy.visit('/cola')
    cy.wait('@colaRota')

    cy.porDato('error-cola')
      .should('be.visible')
      .and('contain', 'No pudimos cargar la cola')

    // Nada de codigos tecnicos en la cara del usuario
    cy.porDato('error-cola').should('not.contain', '500')
    cy.porDato('ticket').should('not.exist')

    // Segunda respuesta: el servidor vuelve. La nueva intercepcion
    // sobre la misma ruta reemplaza a la anterior.
    cy.intercept('GET', '/api/tickets', { fixture: 'cola-recuperada.json' }).as('colaSana')
    cy.porDato('reintentar').click()
    cy.wait('@colaSana')

    cy.porDato('error-cola').should('not.exist')
    cy.porDato('ticket').should('have.length', 1)
    cy.contains('[data-cy="ticket"]', 'Boton de descarga sin respuesta').should('be.visible')
  })
})

La regla de oro, en una frase

Un test E2E describe lo que una persona hace, no lo que el código hace.

Si al leerlo entiendes qué hace el usuario sin abrir la aplicación, está bien escrito. Si necesitas saber cómo está construida la pantalla para entender qué prueba, escribiste una prueba unitaria disfrazada — lenta, frágil y en el lugar equivocado.

Repásalo con cada suite E2E que escribas

  • El escenario cubre un caso de uso completo, no un detalle interno.
  • Parte de un estado conocido y no depende de ningún otro test.
  • Todos los selectores son data-cy.
  • No hay una sola espera por tiempo.
  • Están cubiertos el camino feliz, el error y el vacío.
  • Corre dos veces seguidas y da el mismo resultado.
  • Si falla, el nombre del test ya te dice qué se rompió.
  • Existe porque, si se rompe, no se puede publicar.
