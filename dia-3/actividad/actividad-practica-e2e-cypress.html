Módulo 7 · Lección 4 · Actividad práctica III

Los Aromos: probar la reserva de canchas de principio a fin

En las actividades anteriores probaste piezas sueltas de código, sin navegador. Acá es al revés: la aplicación se levanta entera y tú escribes un programa que la usa como la usaría un socio del complejo — entra, filtra, reserva — y comprueba que hace lo que promete.

Cinco requisitos, 22 escenarios. Todo con Cypress, sin trucos y sin conocimientos previos de pruebas: lo que necesitas está en la práctica en vivo de hoy y en este documento.

Este documento no trae los escenarios resueltos. Trae la aplicación que hay que probar, la lista de casos y los criterios con los que se revisa tu entrega.

El encargo

El Complejo Deportivo Los Aromos arrendaba sus canchas por WhatsApp. Este año estrenó una aplicación: el socio entra con su correo, ve las canchas libres del día, filtra por tipo y reserva la que quiera.

Hay una regla del complejo, y es la que importa: cada socio puede tomar como máximo dos canchas al día. Sin eso, tres personas se llevan el recinto completo y el resto se queda afuera.

La aplicación está entregada y no tiene ni una prueba. Te contratan para cubrirla antes de que se abra al público el lunes.

Hay un defecto escondido. Uno solo.

Está en la pantalla de canchas y tiene que ver con la regla de las dos reservas. No te voy a decir cuál es.

Si escribes los escenarios que se te piden, uno de tus tests se va a poner rojo. Cuando pase: arreglas la aplicación, nunca el test, y lo cuentas en el README.

Pista de método, no de contenido: cuando una regla dice «máximo N», en el código hay casi siempre una comparación con ese N. Los defectos de esta familia no viven en el número — viven en el signo de la comparación. Léela en voz alta antes de creerle.

Qué se evalúa y qué no.

Se evalúa que tus escenarios describan lo que hace una persona, no cómo está construida la pantalla; que ningún test dependa de otro; y que no haya ni una espera por tiempo.

Se evalúa también que todos los selectores sean data-cy. Un test que pasa buscando por clase CSS igual se descuenta: pasa hoy y se cae en el próximo rediseño.

No se evalúa la cantidad de tests. Veintidós escenarios bien elegidos valen más que sesenta repetidos — en end-to-end, de más es un defecto, no una virtud.

La configuración de Vite, con el servidor de datos de la clase adentro. Ese servidor guarda las canchas en memoria y responde en /api. Fíjate en /api/reset: es la dirección que te va a permitir que cada escenario parta desde el mismo punto.

vite.config.js 
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

// ── SERVIDOR DE DATOS DE LA CLASE ─────────────────────────────────
// Cuatro canchas libres y un contador de reservas del dia.
// Todo en memoria: al apagar el servidor se olvida.
const SEMILLA = () => ([
  { id: 'C-01', nombre: 'Cancha 1', tipo: 'futbolito', hora: '19:00', valor: 24000 },
  { id: 'C-02', nombre: 'Cancha 2', tipo: 'futbolito', hora: '20:00', valor: 24000 },
  { id: 'C-03', nombre: 'Cancha 3', tipo: 'padel',     hora: '19:30', valor: 16000 },
  { id: 'C-04', nombre: 'Cancha 4', tipo: 'padel',     hora: '21:00', valor: 18000 }
])

function apiDeClase() {
  let canchas = SEMILLA()
  let reservasDelDia = 0

  const leerCuerpo = (req) => new Promise((listo) => {
    let crudo = ''
    req.on('data', (trozo) => { crudo += trozo })
    req.on('end', () => listo(crudo ? JSON.parse(crudo) : {}))
  })

  return {
    name: 'api-de-clase',
    configureServer(server) {
      // Al montar en '/api' el prefijo se recorta:
      // /api/canchas llega aca como /canchas.
      server.middlewares.use('/api', async (req, res, next) => {
        const ruta = req.url.split('?')[0]
        res.setHeader('Content-Type', 'application/json')

        if (req.method === 'POST' && ruta === '/acceso') {
          const { correo, clave } = await leerCuerpo(req)
          const ok = correo === 'vecino@losaromos.cl' && clave === 'cancha2026'
          res.statusCode = ok ? 200 : 401
          return res.end(JSON.stringify(
            ok ? { token: 'token-de-clase', nombre: 'Rosa Miranda' }
               : { mensaje: 'Correo o clave incorrectos' }
          ))
        }

        if (req.method === 'GET' && ruta === '/canchas') {
          return res.end(JSON.stringify({ canchas, reservasDelDia }))
        }

        if (req.method === 'POST' && /^\/canchas\/[^/]+\/reservar$/.test(ruta)) {
          const id = ruta.split('/')[2]
          canchas = canchas.filter((c) => c.id !== id)
          reservasDelDia = reservasDelDia + 1
          return res.end(JSON.stringify({ ok: true, reservasDelDia }))
        }

        // Deja todo como recien instalado.
        if (req.method === 'POST' && ruta === '/reset') {
          canchas = SEMILLA()
          reservasDelDia = 0
          return res.end(JSON.stringify({ ok: true }))
        }

        next()
      })
    }
  }
}

export default defineConfig({
  plugins: [vue(), apiDeClase()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) }
  },
  // Puerto fijo: si Vite se cambia solo al 5174, la baseUrl de Cypress
  // apunta a ninguna parte y todos tus tests fallan igual.
  server: { port: 5173, strictPort: true }
})

La única salida a la red. Todo lo que la aplicación le pide al servidor pasa por acá. Que sea una sola puerta es lo que después te va a permitir interceptarla desde un test.

src/servicios/api.js 
const BASE = '/api'

export async function entrar(correo, clave) {
  const respuesta = await fetch(`${BASE}/acceso`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ correo, clave })
  })
  const datos = await respuesta.json()
  if (!respuesta.ok) throw new Error(datos.mensaje || 'No pudimos validar tus datos')
  return datos
}

export async function obtenerCanchas() {
  const respuesta = await fetch(`${BASE}/canchas`)
  if (!respuesta.ok) throw new Error('No pudimos cargar las canchas')
  return respuesta.json()
}

export async function reservarCancha(id) {
  const respuesta = await fetch(`${BASE}/canchas/${id}/reservar`, { method: 'POST' })
  if (!respuesta.ok) throw new Error('No pudimos tomar la reserva')
  return respuesta.json()
}

La pantalla de canchas. Es la importante. Tiene el filtro, los cuatro estados y la regla de las dos reservas.

src/vistas/VistaCanchas.vue 
<script setup>
import { computed, onMounted, ref } from 'vue'
import { useRouter } from 'vue-router'
import { obtenerCanchas, reservarCancha } from '@/servicios/api.js'
import { cerrarSesion, socio } from '@/sesion.js'

const LIMITE_DIARIO = 2

const canchas = ref([])
const reservasDelDia = ref(0)
const cargando = ref(false)
const error = ref('')
const tipo = ref('todas')
const router = useRouter()

const visibles = computed(() =>
  tipo.value === 'todas'
    ? canchas.value
    : canchas.value.filter((c) => c.tipo === tipo.value)
)

// Regla del complejo: cada socio toma como maximo 2 canchas al dia.
const limiteAlcanzado = computed(() => reservasDelDia.value > LIMITE_DIARIO)

async function cargar() {
  cargando.value = true
  error.value = ''
  try {
    const datos = await obtenerCanchas()
    canchas.value = datos.canchas
    reservasDelDia.value = datos.reservasDelDia
  } catch {
    error.value = 'No pudimos cargar las canchas. Intenta nuevamente.'
  } finally {
    cargando.value = false
  }
}

async function reservar(id) {
  const datos = await reservarCancha(id)
  reservasDelDia.value = datos.reservasDelDia
  canchas.value = canchas.value.filter((c) => c.id !== id)
}

function salir() {
  cerrarSesion()
  router.push('/acceso')
}

onMounted(cargar)
</script>

<template>
  <main class="canchas">
    <header>
      <h1>Canchas disponibles hoy</h1>
      <p data-cy="socio">{{ socio?.nombre }}</p>
      <p data-cy="contador">Reservas de hoy: {{ reservasDelDia }} de {{ LIMITE_DIARIO }}</p>
      <button data-cy="salir" type="button" @click="salir">Salir</button>
    </header>

    <label for="tipo">Tipo de cancha</label>
    <select id="tipo" data-cy="filtro-tipo" v-model="tipo">
      <option value="todas">Todas</option>
      <option value="futbolito">Futbolito</option>
      <option value="padel">Padel</option>
      <option value="tenis">Tenis</option>
    </select>

    <p v-if="limiteAlcanzado" data-cy="aviso-limite">
      Ya tomaste tus {{ LIMITE_DIARIO }} canchas de hoy.
    </p>

    <p v-if="cargando" data-cy="cargando">Cargando las canchas…</p>

    <div v-else-if="error" data-cy="error-canchas" role="alert">
      <p>{{ error }}</p>
      <button data-cy="reintentar" type="button" @click="cargar">Reintentar</button>
    </div>

    <p v-else-if="visibles.length === 0" data-cy="vacio">
      No hay canchas de ese tipo disponibles.
    </p>

    <ul v-else data-cy="lista">
      <li v-for="c in visibles" :key="c.id" data-cy="cancha" :data-id="c.id">
        <span data-cy="nombre">{{ c.nombre }}</span>
        <span data-cy="tipo">{{ c.tipo }}</span>
        <span data-cy="hora">{{ c.hora }}</span>
        <span data-cy="valor">${{ c.valor }}</span>
        <button
          data-cy="reservar"
          type="button"
          :disabled="limiteAlcanzado"
          @click="reservar(c.id)"
        >Reservar</button>
      </li>
    </ul>
  </main>
</template>

Requisito 1 — Abrir y mirar

Entregable: cypress/e2e/01-primeros-pasos.cy.js · 4 escenarios · Sin escribir en ningún campo todavía.

Qué se necesita

Antes de manejar la aplicación hay que saber mirarla. Estos cuatro escenarios no tocan nada: abren una dirección y comprueban qué se ve. Es el piso de todo lo demás.

#SituaciónQué tienes que comprobar
1Visito /accesoEl título <h1> «Complejo Los Aromos» se ve en pantalla
2Visito /accesoEl formulario se ve, y los campos de correo y clave parten vacíos
3Visito /accesoEl botón dice «Entrar» y está habilitado
4Visito /canchas sin haber entradoTermino en /acceso, con el formulario a la vista

Las herramientas que necesitas

OrdenQué hace
cy.visit('/acceso')Abre esa dirección, como escribirla en la barra y apretar Enter
cy.get('[data-cy="…"]')Busca un elemento por su manilla
cy.contains('h1', 'texto')Busca un <h1> cuyo texto incluya eso

El escenario 4 es el que le da sentido a toda la actividad.

Esa regla —«sin sesión no entras»— no vive en la pantalla de canchas ni en el archivo de sesión: vive en la unión entre el guardia del router y el almacenamiento del navegador. Ninguna prueba de una pieza suelta la habría visto. Ésa es, literalmente, la razón de existir de las pruebas end-to-end.

Sobre el escenario 4: no basta con mirar la dirección.

Un test que solo comprueba la URL puede pasar aunque la pantalla haya quedado en blanco. Comprueba las dos cosas: que la dirección es la del acceso y que el formulario se ve.

Criterios de aceptación

Se revisa esto, uno por uno

  • Los 4 escenarios están dentro de un solo describe con nombre en castellano.
  • Cada it se llama por lo que hace el usuario, no por el comando que usaste. «muestra el formulario de acceso», no «test cy.get».
  • Todos los selectores son data-cy. Cero clases CSS, cero nth-child.
  • El escenario 2 usa have.value con la cadena vacía, no be.empty.
  • El escenario 4 comprueba la dirección y que el formulario se ve.
  • No hay ni un cy.wait con un número.
  • La visita a la dirección está repetida en cada it, o sacada a un beforeEach. Las dos valen; lo que no vale es que un it dependa de que otro haya visitado antes.
El error silencioso que te va a costar puntos: guardar el resultado en una variable. const titulo = cy.get('h1') no te devuelve el título — te devuelve la cadena de Cypress. La comprobación va pegada con un punto: cy.get('h1').should(…).

Requisito 2 — El acceso

Entregable: cypress/e2e/02-acceso.cy.js · 5 escenarios · Acá empiezas a manejar la aplicación.

Qué se necesita

El trámite completo de entrar: con las credenciales buenas, con las malas, con el teclado y saliendo. Es el flujo que más se usa y el que menos se prueba.

#SituaciónQué tienes que comprobar
1 Escribo vecino@losaromos.cl / cancha2026 y hago clic en «Entrar» Llego a /canchas, se ve Rosa Miranda y hay 4 canchas
2 Escribo un correo que no existe y una clave cualquiera Aparece el mensaje «Correo o clave incorrectos», sigo en /acceso y el formulario se ve
3 Ese mismo intento fallido El mensaje no contiene el número 401 ni la palabra «error» en inglés
4 Escribo las credenciales buenas y aprieto Enter, sin tocar el botón Entro igual: llego a /canchas
5 Ya adentro, hago clic en «Salir» Vuelvo a /acceso, y si intento visitar /canchas me devuelve otra vez

Las herramientas nuevas

OrdenQué hace

El escenario 3 parece un capricho y es el más profesional de los cinco.

Un mensaje que le tira al socio del club un «Error 401» no le sirve de nada: no sabe qué hacer con eso. Comprobar que no aparece el número técnico es comprobar que alguien tradujo el fallo a lenguaje humano. Eso es calidad de producto, y se prueba igual que todo lo demás.

Pista sobre el escenario 5.

«Salir» tiene que hacer dos cosas: llevarte a /acceso y borrar la sesión. Si solo comprobaras la primera, un botón que navega pero se olvida de borrar pasaría el test — y cualquiera que escriba /canchas en la barra entraría con la sesión del anterior. Por eso el escenario pide volver a intentar entrar a /canchas.

Criterios de aceptación

Se revisa esto, uno por uno

  • Hay un beforeEach que deja el sistema en estado conocido: cy.request('POST', '/api/reset').
  • El escenario 4 usa {enter} dentro del .type(). No hace clic en el botón.
  • El escenario 2 comprueba las tres cosas: mensaje, dirección y formulario visible.
  • El escenario 5 comprueba que /canchas sigue protegida después de salir.
  • Usas .and() al menos una vez, en vez de repetir el mismo cy.get.
  • Ningún escenario depende de otro: puedes correr cualquiera solo y pasa igual.
  • Sigue sin haber ni un cy.wait con un número.
Te vas a topar con esto: después del clic en «Entrar» pasan varias cosas —cambia la pantalla, sale la petición, llega la respuesta, se dibuja la lista— y todo eso demora. La tentación es meter una espera. No la metas. Cypress ya vuelve a mirar la página hasta que tu comprobación se cumple. Si te sale rojo, el problema es tu selector, no el tiempo.

Requisito 3 — La lista y el filtro

Entregable: cypress/e2e/03-lista.cy.js · 5 escenarios · Acá aparece el estado vacío.

Qué se necesita

La pantalla de canchas con datos reales: contarlas, revisarlas una por una y filtrarlas por tipo. Acuérdate de la tabla del Paso 5: 4 canchas, 2 de futbolito, 2 de pádel, ninguna de tenis.

#SituaciónQué tienes que comprobar
1Entro y llego a la listaHay exactamente 4 canchas
2Reviso la lista completaCada cancha muestra nombre, tipo, hora y valor no vacíos, y su botón «Reservar» está habilitado
3Elijo Padel en el filtroQuedan 2, y son C-03 y C-04
4Elijo Tenis en el filtroNo queda ninguna cancha y aparece el estado vacío
5Vuelvo a TodasVuelven las 4: el filtro esconde, no borra

Las herramientas nuevas

OrdenQué hace
.select('padel')Elige una opción de un <select>. Va el valor de la opción, no lo que se lee en pantalla
.should('have.length', 4)Cuántos elementos coinciden con el selector
.each((fila) => { … })Recorre todos los encontrados, uno por uno
cy.wrap(fila)Le devuelve los poderes de Cypress al elemento que recibiste dentro del .each()
.should('not.be.empty')El elemento tiene algo escrito adentro
[data-cy="cancha"][data-id="C-03"]Apunta a una cancha concreta sin contar posiciones
Ojo con los valores del filtro.

En pantalla se lee «Padel», pero el valor de la opción es padel — en minúscula. .select() quiere el valor. Si le pasas lo que se ve, Cypress te va a decir que esa opción no existe.

Por qué el escenario 4 vale doble.

El estado vacío es de los que nadie prueba a mano —hay que buscar una combinación que no devuelva nada— y de los que más se rompen. Una pantalla que en vez de decir «no hay canchas de ese tipo» se queda en blanco parece caída, y el socio cierra la aplicación creyendo que no anda.

Comprueba las dos caras: que no hay ninguna tarjeta y que el mensaje sí se ve. Una sola de las dos no alcanza.

Pista sobre el escenario 2.

Dentro del .each(), la variable que recibes no es una cadena de Cypress: es el elemento pelado. Si le encadenas un .find() directo, no espera, no reintenta y no aparece en el panel. Envuélvelo primero.

Criterios de aceptación

Se revisa esto, uno por uno

  • El escenario 2 usa .each() con cy.wrap() adentro. No repite cuatro bloques copiados.
  • El escenario 3 identifica las canchas por data-id, no por .first(), .eq() ni posición.
  • El escenario 4 comprueba las dos caras: ninguna tarjeta y el mensaje visible.
  • Para «no hay ninguna tarjeta» usas not.exist, no not.be.visible.
  • El .select() recibe el valor de la opción (padel, tenis), no el texto que se lee.
  • El beforeEach reinicia los datos y entra. Los 5 escenarios parten del mismo punto.
  • El escenario 5 demuestra que filtrar no pierde datos.
La diferencia que te va a morder: cuando un elemento desaparece con v-if, se va de la página → not.exist. Cuando solo queda escondido, sigue ahí → not.be.visible. Elegir el equivocado te da un test rojo sin que nada esté roto, y vas a perder media hora buscando el error donde no está.

Requisito 4 — Cuando el servidor falla

Entregable: cypress/e2e/04-servidor.cy.js · 5 escenarios · Acá aparece cy.intercept.

Qué se necesita

Hasta ahora el servidor siempre te contestó bien. En la vida real se cae, demora, o devuelve una lista vacía. Ésos son los estados que nadie prueba —porque cuesta provocarlos a mano— y son los que se rompen. Con cy.intercept cada uno sale en una línea.

#SituaciónQué tienes que comprobar
1 Todo normal, pero escuchando la petición de canchas La respuesta llega con estado 200 y después se ven las 4 canchas
2 El servidor se cae: contesta 500 Se ve el mensaje de error, hay botón «Reintentar», no hay ninguna cancha y el mensaje no contiene «500»
3 Después de ese error, hago clic en «Reintentar» y ahora el servidor sí responde El error desaparece y se ven las 3 canchas del archivo de datos
4 El servidor responde bien, pero sin ninguna cancha libre Aparece el estado vacío y ninguna tarjeta
5 El servidor se demora 1,5 segundos en contestar Antes se ve «Cargando las canchas…»; después de que contesta, ya no

Cómo se usa cy.intercept

la pantalla pide→ Cypress escucha→ deja pasar · o contesta él mismo · o finge un error→ la pantalla recibe
Lo que quieresCómo se escribe¿Llega al servidor?
Escuchar y poder esperarcy.intercept('GET', '/api/canchas').as('cargar')Sí, pasa de largo
Contestar con datos fijoscy.intercept('GET', '/api/canchas', { body: { … } })No
Contestar desde un archivocy.intercept(…, { fixture: 'canchas-tarde.json' })No
Fingir que se cayócy.intercept(…, { statusCode: 500 })No
Fingir que anda lentocy.intercept(…, { delay: 1500, body: { … } })No
Esperar a que terminecy.wait('@cargar')—
El orden no es negociable: interceptar ANTES de provocar la petición.

cy.intercept instala un oyente. Una petición que salió antes de que el oyente existiera es una petición que Cypress nunca pilló, y tu cy.wait('@alias') se va a quedar esperando hasta rendirse, con el mensaje «no request ever occurred».

En estos cinco escenarios eso significa: primero el cy.intercept, después el cy.visit y el acceso. Nunca al revés.

El archivo de datos que te damos

Para el escenario 3 necesitas una respuesta falsa distinta a la semilla. Cuando los datos inventados pasan de dos líneas, no se escriben dentro del test: se guardan en cypress/fixtures/. Crea este archivo tal cual.

cypress/fixtures/canchas-tarde.json 
{
  "reservasDelDia": 0,
  "canchas": [
    { "id": "C-07", "nombre": "Cancha 7", "tipo": "padel",     "hora": "16:00", "valor": 12000 },
    { "id": "C-08", "nombre": "Cancha 8", "tipo": "padel",     "hora": "17:00", "valor": 12000 },
    { "id": "C-09", "nombre": "Cancha 9", "tipo": "futbolito", "hora": "16:30", "valor": 20000 }

Para el escenario 4 no necesitas archivo.

Una lista vacía cabe en una línea. Acuérdate de la forma que anotaste en la preparación: es un objeto con dos llaves. Si le entregas un arreglo pelado, la pantalla revienta y vas a creer que Cypress está fallando.

Escenario 5: por qué el retardo es la única forma de probar el «Cargando…».

En tu computador el servidor de clase contesta en dos milisegundos: ese mensaje aparece y desaparece antes de que alcances a verlo, y un test tampoco alcanza. Con delay: 1500 le das a la pantalla tiempo suficiente para mostrarlo, y recién ahí se puede comprobar. No es hacer trampa — es la única manera.

Criterios de aceptación

Se revisa esto, uno por uno

  • Todos los cy.intercept están antes del cy.visit.
  • El escenario 1 usa un cy.intercept sin respuesta — solo escucha — y espera el alias.
  • El escenario 2 comprueba las cuatro cosas: mensaje visible, botón «Reintentar», ninguna cancha, y que no aparezca el número 500.
  • El escenario 3 declara una segunda intercepción sobre la misma dirección, después del error. Ése es el mecanismo, no un truco.
  • El escenario 3 usa fixture, no un objeto escrito a mano en el test.
  • El escenario 4 le entrega un objeto con canchas y reservasDelDia, no un arreglo.
  • El escenario 5 comprueba el «Cargando…» antes del cy.wait y su ausencia después.
  • Cero cy.wait con número. Todas las esperas son por alias.
Si un escenario se queda pegado hasta que Cypress lo mata, casi siempre es una de dos: interceptaste después de la petición, o le pusiste el alias a una dirección que no coincide con la que sale de verdad. Abre el panel de cy:open y mira la lista de peticiones: ahí se ve cuál salió y cuál escuchaste.

Requisito 5 — Comandos propios y la regla del negocio

Entregables: cypress/support/commands.js y cypress/e2e/05-reservas.cy.js · 3 escenarios · Acá está el defecto.

Primero: deja de repetirte

A estas alturas todos tus beforeEach se parecen: reiniciar datos, visitar, escribir correo, escribir clave, entrar. Eso es ruido: quien lee el test tiene que saltarse cinco líneas que no dicen nada sobre lo que se está probando.

Cypress deja que te inventes tus propias órdenes. Le enseñas una vez qué significa «entrar» y después escribes cy.entrar() en cualquier test, como si viniera de fábrica.

Forma de un comando propio 
Cypress.Commands.add('nombreDelComando', (parametro) => {
  // Ojo con el `return`: sin el, la cadena se corta y no puedes
  // encadenar .click() ni .should() despues.
  return cy.get(`[data-cy="${parametro}"]`)
})

Tu trabajo en esta parte es escribir tres comandos en cypress/support/commands.js, y comprobar que cypress/support/e2e.js lo importa.

ComandoQué tiene que hacer
cy.reiniciarDatos()Dejar el servidor como recién instalado, con las 4 canchas y el contador en 0
cy.entrar()Hacer el acceso completo con las credenciales del socio y no volver hasta estar en /canchas
cy.reservarCancha(id)Buscar la cancha por su data-id y hacer clic en su botón «Reservar»
La regla para saber si un comando propio vale la pena.

Si esconde una intención del usuario —«entrar», «reservar la cancha X»—, hazlo. Si solo esconde un selector —cy.botonEntrar()—, no: estás inventando un diccionario que nadie va a recordar y que tapa lo que el test hace de verdad.

Después: la regla de las dos reservas

Ahora los tres escenarios. Son pocos y pesados: acá se juega la plata del complejo.

#SituaciónQué tienes que comprobar
1 Reservo la cancha C-01 Desaparece de la lista, quedan 3 canchas y el contador dice «1 de 2»
2 Reservo C-01 y después C-02 Quedan 2 canchas, el contador dice «2 de 2», aparece el aviso del límite y todos los botones «Reservar» quedan deshabilitados
3 Reservo C-03 y recargo la pantalla de canchas C-03 sigue sin aparecer: la reserva quedó guardada de verdad, no solo en pantalla

Un test que se arregla bajándole la exigencia no es un test: es un adorno.

Pista sobre el escenario 3, que es el que más gente escribe mal.

Si recargas la pantalla apenas haces clic, la petición de reserva puede ir todavía en camino y el servidor no alcanza a enterarse: recargas, la cancha vuelve a aparecer, y tu test falla acusando a la aplicación de algo que no hizo.

Antes de recargar, asegúrate de que el servidor recibió la orden. Ya sabes cómo: es lo mismo que hiciste en el Requisito 4 con las peticiones de canchas, pero ahora sobre POST /api/canchas/*/reservar. El * significa «cualquier cosa en ese tramo de la dirección».

Criterios de aceptación

Se revisa esto, uno por uno

  • cypress/support/e2e.js importa ./commands.js.

  • El escenario 2 comprueba que están deshabilitados todos los botones que quedan, no solo el primero.
  • El escenario 3 espera la confirmación del servidor antes de recargar.
  • El defecto está arreglado en VistaCanchas.vue, no tapado en el test.
  • El README explica el defecto en dos líneas: qué estaba mal, qué provocaba y qué escenario lo pilló.
  • La suite completa pasa: 22 escenarios más los 2 del ejemplo.
Por qué el escenario 2 vale por toda la actividad.

El acceso, el filtro y el estado vacío son comodidad. Esto es plata: si la regla de las dos canchas no se cumple, tres socios se llevan el recinto entero un sábado y el resto se queda afuera. Ese tipo de fallo no lo pilla nadie mirando la pantalla, porque parece que todo anda bien.
