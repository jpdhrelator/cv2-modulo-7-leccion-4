Módulo 7 · Lección 4 · Actividad práctica

La Cafetería: el código ya está escrito, faltan las pruebas

Acabas de ver en vivo cómo se prueba una aplicación Vue. Ahora te toca a ti, con un giro: acá no vas a escribir ni una línea de la aplicación. El código de negocio está terminado, funcionando y te lo entregamos completo.

Lo que falta es lo otro: nadie lo probó nunca. Tú escribes la suite de pruebas unitarias con describe, it y expect, usando los tres matchers que vas a ocupar el 90% de tu vida profesional: toBe, toEqual y toHaveLength.

Este documento no trae los tests resueltos. Trae el código a probar, la lista de casos que hay que cubrir y los criterios con los que se va a revisar tu trabajo.

El encargo

La cafetería del instituto tiene una aplicación de pedidos. El módulo que calcula totales, arma el carrito y busca en el catálogo lleva ocho meses en producción y funciona… hasta donde alguien se ha dado cuenta.

La semana pasada un cliente reclamó que le cobraron de más. Nadie pudo demostrar que el cálculo estaba bien, porque no hay un solo test. Se revisó a ojo, se dijo «se ve correcto» y ahí quedó.

Te contratan para eso: cubrir ese módulo con pruebas unitarias. Si el código está bien, tus tests lo demuestran. Si no lo está, tus tests lo delatan.

Lo primero: hay un defecto escondido. Te lo estoy diciendo ahora.

Una de las siete funciones que te entregamos está mal escrita. Una sola. No te voy a decir cuál ni en qué consiste.

Si escribes los casos que se te piden, uno de tus tests va a ponerse rojo. Ese es el momento del ejercicio: no te va a fallar porque escribiste mal el test, te va a fallar porque la función está mala.

Cuando eso pase: arreglas la función, nunca el test. Y lo dejas anotado en el README. Ése es el entregable que más pesa.

Qué se evalúa y qué no.

Se evalúa cómo escribes cada test: si el nombre dice qué comprueba, si prueba una sola cosa, si elegiste el matcher correcto, y si tus tests siguen pasando cuando los corres en otro orden.

No se evalúa la cantidad. Veinte tests que repiten el mismo caso valen menos que ocho bien elegidos. Tampoco se evalúa el porcentaje de cobertura: se evalúa qué cubriste.

Paso 4 — El módulo que tienes que probar (te lo damos entero)

Léelo completo antes de escribir un test. Siete funciones. Una está mala. No empieces a testear por la primera que veas: primero entiende qué promete cada una.
src/dominio/cafeteria.js 
// ══════════════════════════════════════════════════════════════════
//  Reglas de negocio de la cafetería.
//  Todas son funciones PURAS: mismas entradas → misma salida.
//  Ninguna consulta la red, lee el reloj ni escribe en disco.
// ══════════════════════════════════════════════════════════════════

/**
 * Formatea un monto en pesos chilenos: 1500 → "$1.500"
 */
export function formatearPrecio(valor) {
  return '$' + String(valor).replace(/\B(?=(\d{3})+(?!\d))/g, '.')
}

/**
 * Aplica un porcentaje de descuento y redondea al peso más cercano.
 * precioConDescuento(1500, 10) → 1350
 */
export function precioConDescuento(precio, porcentaje) {
  const descuento = precio * (porcentaje / 100)
  return Math.round(precio - descuento)
}

/**
 * Suma el pedido completo: precio × cantidad de cada línea.
 * Un pedido vacío vale 0.
 */
export function totalDelPedido(items) {
  return items.reduce((suma, item) => suma + item.precio * item.cantidad, 0)
}

/**
 * Devuelve un objeto con las tres cifras que muestra el mesón:
 * cuántas líneas distintas, cuántas unidades en total, y cuánto suma.
 */
export function resumenDelPedido(items) {
  return {
    lineas: items.length,
    unidades: items.reduce((suma, item) => suma + item.cantidad, 0),
    total: totalDelPedido(items)
  }
}

/**
 * Agrega un producto del catálogo al pedido.
 * Si el producto ya estaba, sube su cantidad en 1.
 * Si no estaba, lo agrega con cantidad 1.
 * PROMESA: devuelve un pedido NUEVO y no modifica el que recibe.
 */
export function agregarAlPedido(pedido, producto) {
  const existente = pedido.find(item => item.codigo === producto.codigo)

  if (existente) {
    existente.cantidad = existente.cantidad + 1
    return pedido
  }

  return [...pedido, { ...producto, cantidad: 1 }]
}

/**
 * Saca del pedido la línea con ese código.
 * Si el código no está, devuelve el pedido tal cual.
 * PROMESA: devuelve un pedido NUEVO y no modifica el que recibe.
 */
export function quitarDelPedido(pedido, codigo) {
  return pedido.filter(item => item.codigo !== codigo)
}

/**
 * Filtra el catálogo por nombre. No distingue mayúsculas
 * y no le molestan los espacios sobrantes.
 * Con texto vacío devuelve el catálogo completo.
 */
export function buscarPorNombre(catalogo, texto) {
  const busqueda = texto.trim().toLowerCase()
  if (busqueda === '') return catalogo

  return catalogo.filter(producto =>
    producto.nombre.toLowerCase().includes(busqueda)
  )
}

/**
 * Agrupa los NOMBRES del catálogo por categoría.
 * agruparPorCategoria([...]) → { bebidas: ['Café americano', ...], ... }
 */
export function agruparPorCategoria(catalogo) {
  return catalogo.reduce((grupos, producto) => {
    if (!grupos[producto.categoria]) grupos[producto.categoria] = []
    grupos[producto.categoria].push(producto.nombre)
    return grupos
  }, {})
}

Paso 5 — El test de ejemplo, resuelto

Éste es el único test que te entrego escrito. Es el molde: cópialo, córrelo, y a partir de ahí todo lo demás lo escribes tú.

tests/dominio/formatearPrecio.test.js 
import { describe, it, expect } from 'vitest'
import { formatearPrecio } from '@/dominio/cafeteria.js'

// describe = el grupo. Se nombra con la unidad que estás probando.
describe('formatearPrecio', () => {

  // it = un caso. Se nombra con la frase "[qué hace] cuando [situación]".
  it('separa los miles con punto', () => {
    // Arrange — preparo la entrada
    const valor = 1500

    // Act — ejecuto la unidad UNA vez
    const resultado = formatearPrecio(valor)

    // Assert — comparo con lo que el negocio espera
    expect(resultado).toBe('$1.500')
  })

  it('no agrega separador cuando el monto tiene tres dígitos o menos', () => {
    expect(formatearPrecio(950)).toBe('$950')
  })

  it('separa los millones con dos puntos', () => {
    expect(formatearPrecio(1000000)).toBe('$1.000.000')
  })
})

La chuleta: qué matcher para qué

MatcherÚsalo cuando la función devuelve…Ejemplo
toBe Un número, un texto o un booleano expect(total).toBe(5500)
toEqual Un objeto o un arreglo, y quieres comparar su contenido completo expect(resumen).toEqual({ lineas: 2, unidades: 3, total: 5500 })
toHaveLength Un arreglo o un texto, y sólo te importa cuántos expect(resultados).toHaveLength(2)
La regla que te va a salvar de la mitad de los errores:

toBe pregunta «¿son el mismo objeto en memoria?». toEqual pregunta «¿tienen el mismo contenido?».

Por eso expect({ a: 1 }).toBe({ a: 1 }) falla aunque se vean idénticos: son dos objetos distintos. Y por eso expect(5500).toEqual(5500) pasa, pero es una señal de que no entendiste la diferencia.

Criterios de aceptación

Se revisa esto, uno por uno

  • Hay un solo describe, y se llama 'totalDelPedido'.
  • Hay cinco it, uno por cada fila de la tabla.
  • Todos usan toBe. Ninguno usa toEqual.
  • Cada it tiene una sola aserción. Nada de meter tres casos en un test.
  • El nombre de cada it describe la regla de negocio, no el dato: «devuelve cero cuando el pedido está vacío», no «prueba 3».
  • El caso del pedido vacío está cubierto. Sin ese test, este requisito no se aprueba.
  • Los cinco pasan en verde.
Por qué el pedido vacío no es opcional.

Un carrito recién abierto está vacío. Es el estado en el que más tiempo pasa la aplicación y es donde se rompen las funciones que suman: si alguien cambia el reduce y se olvida del valor inicial, el total pasa a ser undefined y el mesón muestra «Total: $undefined».

La regla general: vacío, uno, y muchos. Si cubres esos tres, cubriste el 80% de los errores reales.

Requisito 2 — El resumen del pedido

Entregable: tests/dominio/resumenDelPedido.test.js · Matcher: toEqual · 4 casos.

Qué se necesita

resumenDelPedido(items) devuelve un objeto con las tres cifras del mesón. Como devuelve un objeto, toBe ya no sirve — y eso es justamente lo que este requisito quiere que descubras con las manos.

#SituaciónEntradaResultado esperado
1Dos líneas, tres unidades [{precio:1500,cantidad:2},{precio:2500,cantidad:1}] { lineas: 2, unidades: 3, total: 5500 }
2Pedido vacío [] { lineas: 0, unidades: 0, total: 0 }
3Una línea con muchas unidades [{precio:1200,cantidad:6}] { lineas: 1, unidades: 6, total: 7200 }
4Sólo la cifra de unidades importa El pedido del caso 1 Comprobar únicamente que unidades vale 3, con toBe
Antes de escribirlo bien, escríbelo mal a propósito.

En el primer test, prueba primero con toBe en vez de toEqual. Corre la suite y lee el mensaje de error completo. Vas a ver algo así:

Terminal — el error que tienes que provocar y leer 
npm test

 × resumenDelPedido > entrega las tres cifras del pedido

   AssertionError: expected { lineas: 2, unidades: 3, total: 5500 }
   to be { lineas: 2, unidades: 3, total: 5500 } // Object.is equality

   If it should pass with deep equality, replace "toBe" with "toEqual"
Se ven idénticos y aun así falla.

Ésa es la lección de este requisito, y no se aprende leyéndola: se aprende viendo el error una vez. toBe compara identidad — «¿es exactamente el mismo objeto?». Y no lo es: la función acaba de crear uno nuevo.

Anota en el README lo que hiciste acá. Es parte de la entrega.

Criterios de aceptación

Se revisa esto, uno por uno

  • Los casos 1, 2 y 3 usan toEqual y comparan el objeto completo, con las tres claves.
  • El caso 4 usa toBe sobre resumen.unidades. Ese es el uso correcto de toBe acá.
  • Ningún test compara el objeto completo con toBe.
  • El pedido vacío devuelve las tres claves en cero, no un objeto vacío. Tu test lo demuestra.
  • Los nombres de los it los escribiste tú y describen el comportamiento.
  • En el README explicas, en dos líneas, por qué el caso 4 usa un matcher distinto.
La pregunta que decide el matcher.

«¿Qué me devuelve esta función: un valor suelto o una estructura?» Valor suelto → toBe. Estructura → toEqual. No hay un tercer caso.

Los datos con los que trabajas

Usa este pedido de partida. Ojo con cómo lo declaras: si lo dejas como una constante compartida entre todos los it, un test va a ensuciar al siguiente y vas a perder media hora. Piensa dónde ponerlo.

Pista sobre el caso 5, que es el difícil.

«No modifica el original» no se comprueba mirando lo que devuelve la función. Se comprueba mirando el arreglo que le pasaste, después de haberla llamado. Guarda cómo estaba antes, llama a la función, y compara.

Uno de tus siete tests se va a poner rojo. Es a propósito.

Cuando pase: no toques el test. Lee la función, entiende por qué incumple lo que su propia documentación promete, y arregla la función.

Después vuelve a correr la suite completa. Si arreglaste bien, los siete pasan y ningún otro requisito se rompe. Si algún test de otro requisito se cae, tu arreglo rompió otra cosa: eso también es información valiosa.

Criterios de aceptación

Se revisa esto, uno por uno

  • Hay dos describe: uno por función. No los mezclas en uno solo.
  • Los casos de «cuántas líneas quedan» usan toHaveLength, no resultado.length con toBe.
  • El caso 2 usa toEqual sobre la línea agregada, con sus cinco campos: los cuatro del catálogo más cantidad. Si te falla, cuenta las claves antes de dudar de la función.
  • El caso 5 comprueba el arreglo original después de llamar a la función.
  • Cada it arranca con datos frescos: usas beforeEach o una función que arma el pedido. No hay una constante compartida que los tests modifiquen.
  • Puedes correr cualquier it solo, con it.only, y pasa igual.
  • Encontraste el defecto, lo arreglaste en la función y lo documentaste en el README: qué función era, qué prometía, qué hacía en realidad y cómo lo arreglaste.
Por qué toHaveLength y no .length con toBe.

Las dos funcionan. Pero cuando falla, expect(pedido).toHaveLength(3) te dice «esperaba largo 3, recibí largo 2» y además te imprime el arreglo. Con expect(pedido.length).toBe(3) sólo te dice «esperaba 3, recibí 2» y te quedas sin saber qué había adentro.

Un buen test no sólo detecta el error: te ayuda a entenderlo sin abrir el depurador.

Requisito 4 — La búsqueda del catálogo

Entregable: tests/dominio/buscarPorNombre.test.js · Los tres matchers juntos · 6 casos.

Qué se necesita

buscarPorNombre(catalogo, texto) filtra el catálogo. Importa el CATALOGO de src/dominio/catalogo.js y trabaja con los seis productos reales: no inventes datos nuevos.

#BúsquedaQué tiene que pasarMatcher sugerido
1'café'Devuelve 2 productostoHaveLength
2'CAFÉ'Devuelve los mismos 2: no distingue mayúsculastoHaveLength
3' jugo 'Devuelve 1, y es el Jugo natural: ignora los espacios sobrantestoHaveLength + toBe
4'pizza'Devuelve un arreglo vacío, no null ni undefinedtoHaveLength
5'' (texto vacío)Devuelve el catálogo completo: los 6toHaveLength
6'alfajor'Devuelve exactamente el objeto del alfajor, con sus cuatro campostoEqual
El caso 4 tiene truco.

«Devuelve un arreglo vacío» y «no devuelve nada» se ven igual en la pantalla, pero rompen la aplicación de formas distintas: sobre undefined no se puede hacer .map(). Tu test tiene que distinguirlos. Con toHaveLength(0) lo distingues, porque undefined no tiene largo y el test falla.

Y el caso 6 también.

La función devuelve un arreglo de un elemento, no el elemento. Piensa qué estás comparando exactamente: toEqual([{...}]) no es lo mismo que toEqual({...}). Cualquiera de los dos puede ser correcto; tú decides y lo justificas.

Criterios de aceptación

Se revisa esto, uno por uno

  • Importas CATALOGO desde @/dominio/catalogo.js. No copiaste los datos dentro del test.
  • Los seis casos están cubiertos, cada uno en su propio it.
  • Usaste los tres matchers al menos una vez en este archivo.
  • El caso 5 comprueba toHaveLength(6), es decir, que el texto vacío no filtra nada.
  • Ningún test da por hecho el orden de los resultados salvo que lo compruebes a propósito.
  • El nombre de cada it dice qué situación cubre, no qué texto busca.
Este archivo es el que más se parece a un test de verdad.

Un buscador tiene mayúsculas, espacios, resultados vacíos y una búsqueda en blanco. Son cuatro formas distintas de romperlo y ninguna se te ocurre mirando el código: se te ocurren pensando en el cliente parado frente al mesón.

Requisito 5 — Bordes y agrupación

Entregable: tests/dominio/precioConDescuento.test.js y tests/dominio/agruparPorCategoria.test.js · 9 casos en total.

Parte A — precioConDescuento: los valores frontera

Acá no hay estructuras: todo devuelve un número y todo va con toBe. Lo difícil no es el matcher, es elegir los casos.

#EntradaEsperadoPor qué este caso
1(1500, 10)1350El caso normal
2(1200, 0)1200Descuento cero: no cambia nada
3(3900, 100)0Descuento total: el otro extremo
4(1999, 10)1799Da 1799.1: se redondea hacia abajo
5(1005, 10)905Da 904.5 exacto: ¿hacia dónde redondea?
6(2500, 20)2000Cifra redonda, sin decimales de por medio
El caso 5 es el que separa un test escrito con la cabeza de uno copiado.

904.5 está justo en la mitad. Math.round redondea el medio hacia arriba, así que da 905. Compruébalo tú antes de escribir el expect: si el día de mañana alguien cambia Math.round por Math.floor, este test es el único que se daría cuenta.

Parte B — agruparPorCategoria: objetos con arreglos adentro

Devuelve un objeto cuyas propiedades son arreglos. Es la estructura más compleja de toda la actividad y también la más común en la vida real.

#Qué comprobarMatcher
7 Con el CATALOGO completo, el resultado es exactamente:
{ bebidas: ['Café americano','Café cortado','Jugo natural'], snacks: ['Empanada de pino','Sándwich de ave'], dulces: ['Alfajor'] }		 toEqual
8 Hay tres categorías. Pista: Object.keys(resultado) es un arreglo. toHaveLength
9 La categoría bebidas tiene 3 productos y dulces tiene 1 toHaveLength
Un caso extra que vale puntos: el catálogo vacío.

agruparPorCategoria([]) devuelve {}. ¿Con qué matcher lo compruebas? toEqual({}) funciona; toHaveLength(0) no, porque un objeto no tiene largo. Escríbelo y explica en el README por qué elegiste el que elegiste.

La prueba de que tus tests sirven: rómpelos a propósito.

Cuando termines, entra a cafeteria.js y cambia algo pequeño: un + por un -, un >= por un >, borra un .toLowerCase(). Corre la suite.

Si nada se pone rojo, tus tests no están probando nada. Devuelve el cambio y escribe el test que faltaba. Esto se llama mutation testing hecho a mano, y es la mejor forma de saber si una suite tiene valor real.

Si terminas antes

Extras, en orden de dificultad

  1. Convierte el requisito 5A en una tabla. Los seis casos de precioConDescuento son la misma regla con datos distintos: reescríbelos con it.each en un solo bloque. Compara cuánto código te ahorraste.
  2. Cobertura. Instala @vitest/coverage-v8, corre npx vitest run --coverage y abre el informe. Busca la línea de cafeteria.js que ningún test toca y escribe el test que falta.
  3. Un caso que nadie cubrió. ¿Qué pasa si precioConDescuento recibe un porcentaje de 150? Escribe el test que documente el comportamiento actual. Después decide si eso debería pasar, y si no, arréglalo — pero primero el test.
  4. TDD de verdad. El negocio pide una función nueva: lineaMasCara(items), que devuelve la línea de mayor precio × cantidad, o null si el pedido está vacío. Escribe primero los tests —los tres: vacío, una línea, varias— míralos fallar, y recién ahí implementa.
  5. El empate. ¿Qué debe devolver lineaMasCara si dos líneas suman exactamente lo mismo? El requisito no lo dice. Decide tú, escríbelo como test, y anota la decisión en el README. Eso es lo que hace un desarrollador senior: no adivinar en silencio, sino dejar la decisión escrita donde alguien pueda discutirla.
Lo que se lleva quien hace bien esta actividad.

No es la sintaxis de Vitest: eso se aprende en veinte minutos. Es la costumbre de preguntarse «¿qué caso haría fallar esto?» antes de dar algo por terminado.

El defecto que buscaste hoy estaba escondido detrás de una función que se veía perfectamente razonable, y llevaba ocho meses en producción. Se destapó porque alguien escribió el test que preguntaba lo correcto. Eso es todo el oficio.
