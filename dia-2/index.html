Módulo 7 · Lección 4 · Actividad práctica II

El Mesón: aislar la unidad con spies, stubs y mocks

En la primera actividad probaste funciones puras: entraban datos, salían datos, y no había nada que estorbara. Se acabó la parte fácil.

Acá el código habla con un servidor, registra telemetría, dibuja en un canvas, navega con el router y guarda con retardo. Cinco dependencias que un test unitario no puede ejecutar. Tu trabajo es reemplazarlas: vi.fn(), vi.spyOn(), global.stubs y vi.mock().

Este documento no trae los tests resueltos. Trae el código a probar, la lista de casos y los criterios con los que se revisa.

El encargo

La cafetería creció. Ahora tiene un mesón digital: una pantalla táctil donde el cajero arma el pedido tocando productos, lo cobra y manda la boleta a imprimir.

La versión anterior —la de las funciones puras que probaste— quedó cubierta. Esta capa no tiene ni un test, y es la que de verdad puede cobrar de más: acá viven las llamadas al servidor.

Te contratan para cubrirla. La dificultad no es escribir expect: es decidir qué doble usar para cada dependencia y no ejecutar nada real.

Otra vez: hay un defecto escondido. Uno solo.

Está en el componente grande del Requisito 6 y es de los que le cuestan plata a alguien. No te voy a decir cuál es.

Si escribes los casos que se te piden, uno de tus tests va a ponerse rojo. Ahí: arreglas el componente, nunca el test, y lo documentas en el README.

Pista de método, no de contenido: cuando revises ese componente, busca una variable que se declara, se asigna y no la usa nadie. Eso casi siempre significa que alguien empezó a escribir una protección y no la terminó.

Qué se evalúa y qué no.

Se evalúa que elijas el doble más liviano que resuelva el problema: antes spy que stub, antes stub que mock. Un vi.mock donde bastaba un vi.fn() es un error, aunque el test pase.

Se evalúa también que ningún test ejecute nada real: ni una petición, ni un setTimeout de verdad, ni una línea escrita en la consola.

No se evalúa la cantidad de tests ni el porcentaje de cobertura.

Paso 4 — El dominio (te lo damos entero)

src/dominio/caja.js 
import { telemetria } from '@/servicios/telemetria.js'

/**
 * Cierra la caja del turno: cuenta los pedidos, suma los totales
 * y deja constancia en telemetría.
 */
export function cerrarCaja(pedidos) {
  const total = pedidos.reduce((suma, pedido) => suma + pedido.total, 0)
  const resumen = { pedidos: pedidos.length, total }

  telemetria.registrar('caja_cerrada', resumen)

  return resumen
}
src/dominio/cobro.js 
/**
 * Cobra un pedido contra una pasarela de pago.
 * La pasarela NO se importa: llega como parámetro. Eso es inyección de
 * dependencias, y es lo que hace esta función testeable sin vi.mock.
 *
 * pasarela.pagar(monto) devuelve una promesa con:
 *   { aprobado: true,  codigo: 'TRX-9' }
 *   { aprobado: false, motivo: 'Fondos insuficientes' }
 */
export async function cobrar(pedido, pasarela) {
  if (pedido.total <= 0) {
    throw new Error('El pedido está vacío')
  }

  const respuesta = await pasarela.pagar(pedido.total)

  if (!respuesta.aprobado) {
    return { estado: 'rechazado', motivo: respuesta.motivo }
  }

  return { estado: 'pagado', codigo: respuesta.codigo }
}

<script setup>
import { computed } from 'vue'

const props = defineProps({
  item:   { type: Object, required: true },
  maximo: { type: Number, default: 9 }
})

// Este componente NO recibe callbacks: avisa con eventos.
// Es la diferencia con BotonProducto, y decide cómo se prueba cada uno.
const emit = defineEmits(['cambiar', 'quitar'])

const subtotal = computed(() => props.item.precio * props.item.cantidad)

function subir() {
  if (props.item.cantidad >= props.maximo) return
  emit('cambiar', { codigo: props.item.codigo, cantidad: props.item.cantidad + 1 })
}

function bajar() {
  // Bajar de 1 no deja el pedido en cero: saca la línea entera
  if (props.item.cantidad <= 1) {
    emit('quitar', props.item.codigo)
    return
  }
  emit('cambiar', { codigo: props.item.codigo, cantidad: props.item.cantidad - 1 })
}
</script>

<template>
  <div class="linea" :data-test="`linea-${item.codigo}`">
    <span data-test="nombre">{{ item.nombre }}</span>

    <button data-test="bajar" type="button" aria-label="Quitar una unidad" @click="bajar">−</button>
    <span data-test="cantidad">{{ item.cantidad }}</span>
    <button
      data-test="subir"
      type="button"
      aria-label="Agregar una unidad"
      :disabled="item.cantidad >= maximo"
      @click="subir"
    >+</button>

    <span data-test="subtotal">{{ subtotal }}</span>
  </div>
</template>

tests/componentes/ejemplo.test.js 
import { describe, it, expect, vi } from 'vitest'
import { mount } from '@vue/test-utils'
import BotonProducto from '@/componentes/BotonProducto.vue'

const CAFE = { codigo: 'BEB-01', nombre: 'Café americano', precio: 1500 }

describe('BotonProducto — ejemplo resuelto', () => {

  it('muestra el nombre del producto que recibe', () => {
    const wrapper = mount(BotonProducto, {
      props: { producto: CAFE, alAgregar: vi.fn() }
    })

    expect(wrapper.get('[data-test="nombre"]').text()).toBe('Café americano')
  })

  it('avisa al padre cuando lo tocan', async () => {
    // Arrange — el espía: una función vacía que anota todo lo que recibe
    const alAgregar = vi.fn()
    const wrapper = mount(BotonProducto, { props: { producto: CAFE, alAgregar } })

    // Act — el await no es opcional: Vue actualiza el DOM de forma asíncrona
    await wrapper.get('[data-test="producto-BEB-01"]').trigger('click')

    // Assert — el espía sabe cuántas veces lo llamaron y con qué
    expect(alAgregar).toHaveBeenCalledTimes(1)
    expect(alAgregar).toHaveBeenCalledWith(CAFE)
  })
})

Requisito 1 — Montar, mirar e interactuar

Entregable: tests/componentes/ContadorLinea.test.js · Sin ningún doble todavía · 6 casos.

Qué se necesita

Este requisito no lleva vi por ninguna parte. A propósito.

Antes de reemplazar dependencias hay que saber montar un componente y hacerle preguntas: leer lo que pinta, tocarlo, cambiarle las props y revisar qué eventos emitió. Eso lo hace @vue/test-utils solo, sin ayuda de nadie.

Si esto no está firme, los cinco requisitos siguientes se convierten en copiar y pegar. Empieza por acá aunque te parezca lo más fácil del documento.

ContadorLinea es el + / − de cada línea del pedido. Recibe el item por props y avisa con eventos, no con callbacks. Esa diferencia con BotonProducto es justamente la que decide cómo se prueba cada uno.

#SituaciónQué tienes que comprobar
1Se monta con un café de $1.500 y cantidad 2 Se ven el nombre, la cantidad 2 y el subtotal 3000
2Clic en el botón + Emite cambiar una vez, con { codigo: 'BEB-01', cantidad: 3 }
3Clic en − con cantidad 2 Emite cambiar con cantidad 1, y no emite quitar
4Clic en − con cantidad 1 Emite quitar con el código del producto, y no emite cambiar
5La cantidad ya llegó al maximo El botón + está deshabilitado y no se emite nada
6El padre cambia las props: la cantidad pasa a 4 El subtotal en pantalla pasa a 6000

Las cuatro herramientas que necesitas

Cómo se lee emitted()

Anatomía del registro de eventos 
// Después de un clic en "+", esto es lo que hay dentro del wrapper:

wrapper.emitted()
// { cambiar: [ [ { codigo: 'BEB-01', cantidad: 3 } ] ] }

wrapper.emitted('cambiar')
// [ [ { codigo: 'BEB-01', cantidad: 3 } ] ]   ← una entrada por cada emisión

wrapper.emitted('cambiar')[0]
// [ { codigo: 'BEB-01', cantidad: 3 } ]       ← los ARGUMENTOS de la 1ª emisión

wrapper.emitted('cambiar')[0][0]
// { codigo: 'BEB-01', cantidad: 3 }           ← el primer argumento

wrapper.emitted('quitar')
// undefined                                    ← nunca se emitió
Los dos corchetes confunden a todo el mundo la primera vez.

El primero es cuál emisión (un componente puede emitir el mismo evento varias veces). El segundo es cuál argumento (un emit puede llevar varios). Por eso [0][0] significa «el primer argumento de la primera emisión».

Tú decides cuál de las dos formas usas en cada caso. Las dos son válidas; lo que no es válido es escribirlas al azar hasta que el test pase.

Acá no se usa vi.fn(). Y es importante que entiendas por qué.

Vue Test Utils ya registra todas las emisiones por su cuenta: emitted() es un espía que viene puesto de fábrica. Montar un vi.fn() para vigilar un emit es levantar una máquina que ya estaba andando.

La regla que se evalúa en toda la actividad: vi.fn() es para callbacks —funciones que el componente recibe y llama—, y emitted() es para eventos. Confundirlos es el error de criterio más común de esta unidad.

Criterios de aceptación

Se revisa esto, uno por uno

  • En este archivo no aparece vi ni una sola vez. Ni vi.fn, ni vi.mock, ni vi.spyOn.
  • Hay una fábrica de montaje: una función que monta el contador y deja que cada test cambie sólo lo que le importa.
  • Todos los trigger y el setProps llevan await.
  • Los casos 3 y 4 comprueban las dos cosas: el evento que sí salió y el que no. Para el que no, toBeUndefined().
  • El caso 2 compara los argumentos del evento con toEqual, porque son un objeto.
  • El caso 5 comprueba el atributo disabled y que no se emitió nada.
  • El caso 6 usa setProps y vuelve a leer el DOM después.
  • Buscas por data-test, nunca por clase CSS ni por posición (findAll('button')[1]).
Por qué el caso 4 vale por tres.

«Bajar de 1 saca la línea» es una regla de negocio de verdad, de esas que alguien decidió en una reunión. Está a una línea de distancia de su alternativa —dejar la cantidad en cero y una línea fantasma en el pedido— y no se ve en ninguna parte de la interfaz.

Tu test es el único lugar del proyecto donde esa decisión queda escrita.

Requisito 2 — El espía que tú entregas

Entregable: tests/componentes/BotonProducto.test.js · Doble: vi.fn() · 5 casos.

Qué se necesita

BotonProducto recibe la función alAgregar por props. No hay nada que interceptar: la función se la entregas tú al montar. Ése es el caso de vi.fn(), el espía más simple que existe.

#SituaciónQué tienes que comprobar
1Un clic en el botónEl callback se llamó exactamente una vez
2Ese mismo clicSe llamó con el objeto producto completo, no con el código ni con el nombre
3Tres clics seguidosTres llamadas, y la última también trae el producto
4El producto está agotadoEl botón está deshabilitado y el callback no se llama nunca
5Se monta el componente y no se toca nadaEl callback no se llamó

Los datos con los que trabajas

Producto de prueba 
{ codigo: 'SNK-01', nombre: 'Empanada de pino', precio: 2500 }
El caso 5 parece tonto y es el más importante de los cinco.

Comprobar que algo no pasó vale tanto como comprobar que pasó. Un componente que llama al callback durante el onMounted, o dos veces por cada clic, es un error real que sólo se detecta con not.toHaveBeenCalled() y con toHaveBeenCalledTimes().

Pista sobre el caso 4.

Un botón con disabled no dispara click en un navegador real, pero en jsdom la cosa es más sutil. No des por hecho el resultado: escribe el test, córrelo, y comprueba las dos cosas — que el atributo está y que el espía no se llamó. Si te sorprende lo que pasa, anótalo en el README: es exactamente el tipo de detalle que hay que saber.

Criterios de aceptación

Se revisa esto, uno por uno

  • Usas vi.fn(). No usas vi.mock ni vi.spyOn en este archivo: acá sobran.
  • Cada it crea su propio vi.fn(). No hay un espía compartido entre tests.
  • El caso 2 usa toHaveBeenCalledWith con el objeto completo.
  • El caso 3 usa toHaveBeenCalledTimes(3) y toHaveBeenLastCalledWith.
  • El caso 5 usa not.toHaveBeenCalled().
  • Todos los trigger llevan await.
  • Buscas por data-test, nunca por clase CSS.
El error silencioso que te va a costar puntos: expect(alAgregar).toHaveBeenCalled — sin paréntesis. No ejecuta nada y el test pasa siempre, aunque el espía jamás se haya llamado. Un test que nunca falla es peor que no tener test.

Requisito 3 — El efecto invisible

Entregable: tests/dominio/caja.test.js · Doble: vi.spyOn() · 5 casos.

Qué se necesita

cerrarCaja(pedidos) hace dos cosas: devuelve un resumen —eso se ve— y registra en telemetría —eso no se ve por ninguna parte. El segundo efecto es tan parte del contrato como el primero, y sin un espía no hay forma de comprobarlo.

Acá telemetria se importa dentro del módulo: no te la pasan. Por eso vi.fn() no sirve y toca vi.spyOn.

#SituaciónQué tienes que comprobar
1Dos pedidos: [{total: 5500}, {total: 1200}] Devuelve { pedidos: 2, total: 6700 }
2Los mismos dos pedidos Se llamó a telemetria.registrar una vez, con 'caja_cerrada' y { pedidos: 2, total: 6700 }
3Caja vacía: [] Devuelve { pedidos: 0, total: 0 } y registra igual: cerrar una caja sin ventas también es un cierre
4Un solo pedido El primer argumento del registro es exactamente el texto 'caja_cerrada'. Léelo desde mock.calls, no con toHaveBeenCalledWith
5Se cierra la caja tres veces seguidas Tres registros, y el tercero corresponde a la tercera caja
Corre este archivo dos veces: una sin silenciar y otra silenciando.

vi.spyOn(telemetria, 'registrar') deja pasar la llamada original, así que tu salida de tests se va a llenar de líneas [telemetría] caja_cerrada …. Míralo. Ésa es la prueba visible de que un spy no bloquea nada.

Después encadénale .mockImplementation(() => {}) y vuelve a correr: la salida queda limpia. En ese momento tu spy dejó de ser un spy y pasó a ser un stub. Explica esa diferencia en el README, en dos líneas.

Criterios de aceptación

Se revisa esto, uno por uno

  • Usas vi.spyOn(telemetria, 'registrar'). No falsificas el módulo con vi.mock: acá es matar una mosca a cañonazos.
  • Hay limpieza entre tests: restoreMocks: true en el config, o vi.restoreAllMocks() en un afterEach.
  • El caso 3 comprueba las dos cosas: lo que devuelve y que registró igual.
  • El caso 4 lee espia.mock.calls[0][0], para que demuestres que sabes leer el registro a mano.
  • El caso 5 usa toHaveBeenCalledTimes(3) y toHaveBeenLastCalledWith.
  • Ningún test depende de las llamadas que dejó el anterior. Compruébalo corriendo uno solo con it.only.
  • En el README explicas, en dos líneas, la diferencia entre spy y stub que viste en pantalla.
Por qué la limpieza no es opcional.

Un espía instalado sobre telemetria.registrar sigue instalado cuando termina el test. Si no limpias, el siguiente hereda el historial y tu toHaveBeenCalledTimes(1) falla diciendo que hubo cuatro. Vas a revisar el test equivocado durante veinte minutos.

clear borra el historial · reset borra además la implementación falsa · restore devuelve el método original. Sólo restore funciona con vi.spyOn.

Requisito 4 — Dictar la respuesta

Entregable: tests/dominio/cobro.test.js · Doble: stubs de función · 6 casos.

Qué se necesita

cobrar(pedido, pasarela) le pega a una pasarela de pago. Contra la pasarela real esto sería imposible de probar: no puedes pedirle que rechace una tarjeta a voluntad, ni que se caiga justo cuando tú quieres.

Pero la pasarela llega como parámetro. Eso significa que tú decides qué responde. Ahí es donde el spy se convierte en stub: no sólo mira, también contesta.

#Qué responde la pasarelaQué tiene que devolver cobrar
1{ aprobado: true, codigo: 'TRX-9' } { estado: 'pagado', codigo: 'TRX-9' }
2{ aprobado: false, motivo: 'Fondos insuficientes' } { estado: 'rechazado', motivo: 'Fondos insuficientes' }
3Cualquiera Se llamó a pagar una vez y con el monto del pedido, no con el pedido entero
4La pasarela se cae: la promesa se rechaza con 'Timeout de la pasarela' cobrar propaga el error. Se comprueba con rejects
5El pedido tiene total: 0 Lanza 'El pedido está vacío' y a pagar no se le llama nunca
6El cliente reintenta: la primera vez rechaza, la segunda aprueba Dos llamadas a cobrar: la primera devuelve rechazado, la segunda pagado

Cómo se arma la pasarela falsa

La forma del doble — el resto lo escribes tú 
// La pasarela falsa es un objeto con un método espiado.
// Lo que le dictes a ese método decide qué situación estás probando.
const pasarela = { pagar: vi.fn() }

// Y a partir de ahí:
//   .mockResolvedValue(...)      → la promesa se resuelve, siempre igual
//   .mockRejectedValue(...)      → la promesa se rechaza
//   .mockResolvedValueOnce(...)  → sólo para la PRÓXIMA llamada
//
// El caso 6 se resuelve encadenando dos ...Once(). Piensa en qué orden.
El caso 5 es el que más gente escribe mal.

Tiene dos aserciones y las dos importan: que lanza el error, y que pagar no se llamó. La segunda es la que de verdad protege al negocio: si alguien mueve la validación después del await, estarías cobrando pedidos vacíos y el test que sólo mira el mensaje de error ni se entera.

Y ojo con la sintaxis: toThrow recibe una función. Como cobrar es async, va con await expect(cobrar(...)).rejects.toThrow('...').

Criterios de aceptación

Se revisa esto, uno por uno

  • La pasarela falsa se crea con vi.fn(). No hay vi.mock en este archivo, y no hace falta ninguno.
  • Los seis casos están, cada uno en su it.
  • Los casos 1 y 2 usan toEqual, porque cobrar devuelve un objeto.
  • El caso 3 usa toHaveBeenCalledWith(5500) —el monto—, no el objeto pedido.
  • Los casos 4 y 5 usan await expect(...).rejects.toThrow(...).
  • El caso 5 comprueba además expect(pasarela.pagar).not.toHaveBeenCalled().
  • El caso 6 usa mockResolvedValueOnce encadenado, no dos pasarelas distintas.
  • Ningún test espera de verdad: la suite completa corre en milisegundos.
Por qué cobrar recibe la pasarela como parámetro.

Podría haberla importado, como hace caja.js con la telemetría. Pero entonces probarla exigiría vi.mock. Al recibirla, basta con pasarle un objeto falso.

Eso se llama inyección de dependencias, y es una decisión de diseño que se toma pensando en el test. Cuando algo es difícil de probar, casi nunca es culpa del test: es una señal de que el diseño esconde sus dependencias.

Qué se necesita

Stubeas lo que te molesta, no lo que te da flojera.

Lo que se lleva quien hace bien esta actividad.

Un criterio, no una sintaxis: el doble más liviano que resuelva el problema. Spy si sólo quiero mirar. Stub si necesito controlar la respuesta. Mock si el módulo entero no debe ni cargarse. Quien mockea todo por si acaso termina con tests que prueban sus propios mocks.

Y una segunda cosa, más difícil de enseñar: cuando algo es difícil de probar, casi nunca es culpa del test. Es el diseño avisándote que esconde sus dependencias. Fíjate en la diferencia entre cobrar, que recibe la pasarela y se prueba en tres líneas, y MesonView, que importa cinco cosas y necesita media página de preparación.
