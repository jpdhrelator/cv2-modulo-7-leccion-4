Pruebas unitarias en Vue: spies, stubs y mocks con Vitest

Seis demostraciones cortas y una integradora. Cada una parte del problema que resuelve, no de la sintaxis. Los tres conceptos centrales de la lección —spy, stub y mock— tienen un ejercicio propio cada uno, porque confundirlos es el error más caro de esta unidad.

La presentación enseña el stack Vue CLI + Jest / Mocha + Chai + Sinon. Nosotros creamos los proyectos con Vite, así que usaremos Vitest: mismo concepto, misma API de aserciones, y el doble de velocidad. Todo lo que dice la lección sigue valiendo — cambia el nombre de la herramienta, no la idea.

Cómo se dicta esto.

Los ejercicios 1 y 2 son JavaScript puro: sin componentes, sin DOM, sin red. Ahí se entiende qué es una prueba unitaria y qué es TDD. Si esto no queda claro, lo demás es copiar y pegar sin saber por qué.

El 3 introduce @vue/test-utils: montar un componente, mirarlo e interactuar con él. Recién ahí tiene sentido hablar de dobles de prueba.

Del 4 al 6 van los tres dobles, uno por ejercicio, en orden de menor a mayor intervención: spy (mira), stub (responde), mock (reemplaza). La integradora los usa los tres en un mismo componente.

Preparación — Vitest sin Vue CLI

Objetivo: un proyecto Vite con Vitest y Vue Test Utils corriendo, y el primer test en verde. · 15 minutos.

Por qué no usamos vue create

La lección instala el entorno con npm i -g @vue/cli y luego vue create, que abre un menú donde eliges «Unit Testing» y después Jest o Mocha. Es cómodo, pero te esconde la configuración: cuando algo falla, no sabes dónde mirar.

Nosotros usamos Vite, que es lo que la propia documentación de Vue recomienda hoy. Y con Vite viene su compañero natural: Vitest, que reutiliza el mismo vite.config.js. Eso significa que tus alias, tus plugins y tus variables de entorno ya funcionan dentro de los tests sin configurar nada dos veces. Con Jest tendrías que duplicarlo todo.

La configuración: ocho líneas dentro de vite.config.js

vite.config.js 
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],

  // El alias '@' apunta a src/. Vale para la app Y para los tests,
  // porque Vitest lee este mismo archivo. Con Jest habría que repetirlo.
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) }
  },

  test: {
    // Sin esto no hay document ni window: los componentes no se pueden montar.
    environment: 'jsdom',

    // Permite usar describe/it/expect sin importarlos en cada archivo,
    // igual que hace Jest. Aun así, en este material los importo siempre:
    // ver de dónde viene cada cosa vale más que ahorrar una línea.
    globals: true,

    // Código que corre UNA vez antes de toda la suite.
    setupFiles: ['./tests/setup.js'],

    include: ['tests/**/*.test.js'],

    // Higiene automática entre tests. Se explica en detalle en el ejercicio 4.
    clearMocks: true,
    restoreMocks: true,

    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
      include: ['src/**']
    }
  }
})
Ésta es la ventaja concreta de Vitest sobre Jest en un proyecto Vite.

Un solo archivo de configuración. El mismo @, el mismo plugin de Vue, las mismas variables import.meta.env. Con Jest necesitarías además babel-jest, vue-jest, un moduleNameMapper para el alias y un transform para los .vue. Cuatro piezas más que mantener sincronizadas.

Anatomía de una prueba unitaria

Objetivo: entender qué es —y sobre todo qué NO es— una prueba unitaria. · 25 minutos · JavaScript puro, sin Vue.

Empezamos sin componentes a propósito.

La lección define la prueba unitaria como «un test automatizado que comprueba que un método concreto funciona correctamente». Un método concreto. Si tu primer test monta un componente, hace una petición y revisa tres cosas, no estás probando un método: estás probando un sistema, y cuando falle no vas a saber cuál de las cinco piezas se rompió.

El código bajo prueba

Trabajamos con una mesa de soporte. Ésta es la regla de negocio que decide la prioridad de un ticket. Fíjate en lo que no hace: no consulta una API, no lee el reloj, no escribe en ninguna parte. Es una función pura: mismas entradas, misma salida, siempre.

src/dominio/prioridad.js 
// De menor a mayor urgencia. El orden del arreglo ES la escala.
export const PRIORIDADES = ['baja', 'media', 'alta', 'critica']

export function calcularPrioridad({ minutosAbierto, clientePremium, servicioCaido }) {
  if (servicioCaido) return 'critica'
  if (clientePremium && minutosAbierto >= 60) return 'alta'
  if (minutosAbierto >= 240) return 'alta'
  if (minutosAbierto >= 60) return 'media'
  return 'baja'
}

export function ordenarPorPrioridad(tickets) {
  // Copiamos con [...] para NO mutar el arreglo que nos pasaron.
  // Una función que muta lo que recibe es una función difícil de testear.
  return [...tickets].sort(
    (a, b) => PRIORIDADES.indexOf(b.prioridad) - PRIORIDADES.indexOf(a.prioridad)
  )
}
Una función pura es el mejor lugar para empezar a testear, y también la señal de que tu arquitectura está bien. Si las reglas de negocio están enredadas dentro de un componente, para probarlas vas a tener que montar el componente entero. Sácalas a src/dominio/ y se prueban en tres líneas.

La estructura AAA: Arrange, Act, Assert

Todo test tiene tres momentos, y confundirlos es lo que produce tests ilegibles. En español: preparar, ejecutar, comprobar.

Arrange→ preparo los datos que necesita la unidad· Act→ la ejecuto UNA vez· Assert→ comparo el resultado con lo esperado
tests/dominio/prioridad.test.js 
import { describe, it, expect } from 'vitest'
import { calcularPrioridad, ordenarPorPrioridad } from '@/dominio/prioridad.js'

describe('calcularPrioridad', () => {

  it('marca como crítica cualquier caída de servicio, aunque el ticket sea nuevo', () => {
    // Arrange — preparo la entrada
    const ticket = { minutosAbierto: 1, clientePremium: false, servicioCaido: true }

    // Act — ejecuto la unidad, una sola vez
    const prioridad = calcularPrioridad(ticket)

    // Assert — comparo con lo que el negocio dice que debe pasar
    expect(prioridad).toBe('critica')
  })

  it('sube a alta un ticket de cliente premium que lleva una hora abierto', () => {
    const ticket = { minutosAbierto: 60, clientePremium: true, servicioCaido: false }
    expect(calcularPrioridad(ticket)).toBe('alta')
  })

  it('deja en media al cliente normal con una hora abierta', () => {
    const ticket = { minutosAbierto: 60, clientePremium: false, servicioCaido: false }
    expect(calcularPrioridad(ticket)).toBe('media')
  })

  it('parte en baja cuando el ticket recién se abrió', () => {
    const ticket = { minutosAbierto: 0, clientePremium: true, servicioCaido: false }
    expect(calcularPrioridad(ticket)).toBe('baja')
  })
})
El nombre del test es documentación, no un trámite.

Compara it('funciona') con it('marca como crítica cualquier caída de servicio, aunque el ticket sea nuevo'). Cuando este test falle en seis meses, el segundo nombre te dice qué regla de negocio se rompió sin leer una línea de código. El primero te obliga a leerlo todo.

Fórmula que funciona: «[qué hace] cuando [en qué situación]». Nada de «test1», «debería funcionar» ni «prueba de prioridad».

Las seis características que exige la lección, traducidas a decisiones concretas

Un test que parece bueno y no lo es

Este archivo pasa en verde. Y aun así está roto: rompe cuatro de las seis reglas de arriba. Léelo entero antes de mirar los comentarios.

tests/dominio/prioridad.test.js — versión frágil 
import { describe, it, expect } from 'vitest'
import { calcularPrioridad, ordenarPorPrioridad } from '@/dominio/prioridad.js'

// ✗ Estado compartido: vive FUERA de los tests. Lo que hace uno lo hereda el otro.
const cola = []
const inicio = Date.now()

describe('la mesa de soporte', () => {

  it('funciona', () => {                            // ✗ el nombre no dice nada
    cola.push({ id: 1, prioridad: 'baja' })
    expect(cola).toHaveLength(1)

    // ✗ Depende del reloj real: mañana, en otra máquina, da otro número
    const abierto = (Date.now() - inicio) / 60000
    expect(calcularPrioridad({ minutosAbierto: abierto })).toBe('baja')

    cola.push({ id: 2, prioridad: 'critica' })
    // ✗ Este expect solo pasa si la línea 11 se ejecutó antes.
    //   Corre este `it` solo, con it.only, y falla.
    expect(ordenarPorPrioridad(cola)[0].id).toBe(2)

    // ✗ Cinco aserciones de tres conceptos distintos en un solo test:
    //   cuando falle, el reporte te dice "funciona ✗" y nada más.
  })
})

La misma intención, escrita bien

tests/dominio/prioridad.test.js — continuación 
describe('ordenarPorPrioridad', () => {

  // beforeEach corre ANTES de cada it. Cada test arranca con datos nuevos:
  // es lo que garantiza el aislamiento.
  let cola

  beforeEach(() => {
    cola = [
      { id: 1, prioridad: 'baja' },
      { id: 2, prioridad: 'critica' },
      { id: 3, prioridad: 'media' }
    ]
  })

  it('pone primero el ticket más urgente', () => {
    expect(ordenarPorPrioridad(cola)[0].id).toBe(2)
  })

  it('no modifica el arreglo original', () => {
    ordenarPorPrioridad(cola)
    // Si la función mutara la entrada, este test la delataría
    expect(cola.map(t => t.id)).toEqual([1, 2, 3])
  })

  it('devuelve un arreglo vacío si la cola está vacía', () => {
    expect(ordenarPorPrioridad([])).toEqual([])
  })
})
Recuerda importar beforeEach desde vitest (import { describe, it, expect, beforeEach } from 'vitest'), salvo que confíes en globals: true. Es el olvido más común de la primera clase.

Los matchers que vas a usar el 90% del tiempo

MatcherPara quéEjemplo
toBeIdentidad estricta (===). Números, textos, booleanos.expect(total).toBe(3)
toEqualIgualdad profunda. Objetos y arreglos.expect(lista).toEqual([1, 2])
toMatchObjectEl objeto contiene al menos estas claves.expect(t).toMatchObject({ id: 7 })
toContainUn elemento dentro de un arreglo, o un texto dentro de otro.expect(html).toContain('alta')
toHaveLengthLargo de arreglo o texto.expect(cola).toHaveLength(3)
toBeTruthy / toBeFalsyValor verdadero o falso «a la JavaScript».expect(activo).toBeTruthy()
toBeNull / toBeUndefinedAusencia explícita.expect(x).toBeNull()
toThrowQue la función lance un error. Ojo: se le pasa una función.expect(() => f()).toThrow('mensaje')
rejects.toThrowQue una promesa se rechace.await expect(p).rejects.toThrow()
toBeCloseToDecimales, para esquivar el redondeo binario.expect(0.1 + 0.2).toBeCloseTo(0.3)
.notNiega cualquiera de los anteriores.expect(x).not.toBe(0)
toBe con objetos es la trampa clásica.

expect({ id: 1 }).toBe({ id: 1 }) falla: son dos objetos distintos en memoria, aunque se vean iguales. Para objetos y arreglos siempre toEqual. Para números y textos, toBe.

Qué te tiene que quedar claro

  • Una prueba unitaria prueba una unidad: si falla, sabes exactamente qué se rompió.
  • AAA no es decoración: separa preparar, ejecutar y comprobar.
  • El estado compartido fuera de los tests destruye el aislamiento. beforeEach lo resuelve.
  • toBe para primitivos, toEqual para objetos y arreglos.
  • Los valores frontera (59/60) valen más que diez casos del medio.

TDD: rojo, verde, refactor

Objetivo: escribir el test antes que el código y ver por qué eso cambia el diseño. · 25 minutos · JavaScript puro.

La lección lo define bien: «la práctica de escribir las pruebas primero». Suena a formalismo hasta que lo haces una vez. El punto no es la disciplina — es que el test escrito primero te obliga a diseñar la función desde afuera, desde cómo se va a usar, en vez de desde cómo se va a implementar.

🔴 Rojo→ escribo el test del requisito. Falla, porque el código no existe→ 🟢 Verde→ escribo lo MÍNIMO para que pase→ 🔵 Refactor→ limpio sin tocar el test↺

El requisito, dicho por el negocio

«Cada ticket tiene un plazo de atención según su prioridad: crítica 15 minutos, alta 60, media 240 y baja 1440. Quiero saber cuántos minutos quedan antes de incumplir el plazo. Si ya se venció, quiero un número negativo para saber por cuánto nos pasamos.»

🔴 Rojo — el test primero

tests/dominio/sla.test.js 
import { describe, it, expect } from 'vitest'
import { minutosRestantesDeSla } from '@/dominio/sla.js'

describe('minutosRestantesDeSla', () => {

  it('a un ticket de prioridad alta recién abierto le quedan 60 minutos', () => {
    const abiertoEn = new Date('2026-03-10T10:00:00Z')
    const ahora     = new Date('2026-03-10T10:00:00Z')

    const restantes = minutosRestantesDeSla({ prioridad: 'alta', abiertoEn }, ahora)

    expect(restantes).toBe(60)
  })
})
Mira el segundo parámetro: ahora.

Ese parámetro no apareció porque sí. Apareció porque al escribir el test me pregunté «¿respecto de qué momento calculo?», y la única respuesta que produce un test repetible es: el momento me lo pasan, no lo leo yo del reloj. Si hubiera escrito la función primero, casi seguro habría puesto Date.now() adentro y tendría un test que falla según la hora del día.

Esto es lo que quiere decir la lección con «TDD mejora el diseño». No es magia: es que el test te obliga a hacer explícitas las dependencias.

const SLA_EN_MINUTOS = {
  critica: 15,
  alta: 60,
  media: 240,
  baja: 1440
}

const MS_POR_MINUTO = 60000

function minutosEntre(desde, hasta) {
  return (hasta - desde) / MS_POR_MINUTO
}

export function minutosRestantesDeSla(ticket, ahora) {
  const limite = SLA_EN_MINUTOS[ticket.prioridad]

  if (limite === undefined) {
    throw new Error(`Prioridad desconocida: ${ticket.prioridad}`)
  }

  return limite - minutosEntre(ticket.abiertoEn, ahora)
}

export function estaVencido(ticket, ahora) {
  return minutosRestantesDeSla(ticket, ahora) < 0
}

Montar un componente con Vue Test Utils

Objetivo: montar, buscar, interactuar y verificar lo que emite un componente. · 30 minutos · sin dobles todavía.

Todavía no hay mocks acá. A propósito.

La lección presenta Vue Test Utils así: «la librería oficial de Vue para hacer testing». Su trabajo es uno solo — darte acceso a un componente montado: leer su HTML, hacer clic, cambiar props, ver qué eventos emitió. Los dobles de prueba vienen de Vitest, no de aquí. Separar esas dos responsabilidades ahora te ahorra la confusión de los ejercicios 4 a 6.

Qué hace exactamente mount

mount(Componente, opciones) crea una instancia de Vue de verdad, la renderiza en el DOM falso de jsdom, ejecuta su ciclo de vida completo (setup, onMounted…) y te devuelve un wrapper: un envoltorio con métodos para inspeccionarlo.

mount(Componente)→ wrapper→ .find() / .get()→ .text() / .attributes()· .trigger() / .setValue()· .emitted()

El componente bajo prueba

Si buscas por clase CSS (.tarjeta h3), el día que el diseñador renombre la clase se te caen veinte tests que no tienen nada que ver con el diseño. data-test es un contrato explícito entre el componente y su prueba: esto se llama así porque los tests lo buscan por ese nombre. Nadie lo va a renombrar por accidente.

Interactuar: trigger, setValue y el await obligatorio

tests/componentes/TarjetaTicket.test.js — se agrega 
  it('emite "resolver" con el id del ticket al hacer clic', async () => {
    const wrapper = montarTarjeta()

    // trigger() devuelve nextTick(); sin await, compruebas el DOM viejo.

  it('no permite resolver un ticket que ya está resuelto', () => {
    const wrapper = montarTarjeta({ resuelto: true })

    expect(wrapper.get('[data-test="estado"]').text()).toBe('Resuelto')

  it('se actualiza cuando cambian las props desde el padre', async () => {
    const wrapper = montarTarjeta()
    expect(wrapper.get('[data-test="estado"]').text()).toBe('Abierto')

      ticket: { id: 7, titulo: 'No carga el informe mensual', prioridad: 'alta', resuelto: true }

Si un test te falla y el valor «viejo» aparece en el mensaje, te faltó un await.

Vue agrupa las actualizaciones del DOM y las aplica en el siguiente tick. Todos los métodos que cambian estado en Vue Test Utils —trigger, setValue, setProps, setChecked— devuelven una promesa justamente para que puedas esperar ese tick. Ponle await a todos, siempre, sin pensarlo.

Vue Test Utils ya te da un espía de eventos gratis.

emitted() registra todas las emisiones sin que tú prepares nada. Cuando lleguemos a los spies en el ejercicio 4, recuerda esto: para eventos del componente no necesitas vi.fn(). Montar un espía para algo que la librería ya registra es trabajo de más y ruido en el test.

El ciclo de vida: por qué la lección insiste con ese diagrama

La presentación dedica una lámina al ciclo de vida de un componente antes de hablar de Vue Test Utils, y tiene razón: mount() dispara el ciclo completo. Si tu componente pide datos en onMounted, esa petición se ejecuta en el momento en que montas — antes de tu primera aserción.

Qué pasa en cada línea del test 
const wrapper = mount(PanelDeSoporte)
  │
  ├─ setup()      se ejecuta
  ├─ onMounted()  se ejecuta  ← acá sale la petición HTTP de verdad
  └─ primer render

await flushPromises()   ← espera a que se resuelvan las promesas pendientes
  │
  └─ el estado ya tiene los datos y el DOM se re-renderizó

expect(...)             ← recién ahora la aserción ve lo que esperas
Y de ahí nace la necesidad de los dobles de prueba.

Ese «acá sale la petición HTTP de verdad» es el problema. Un test unitario no puede depender de un servidor: sería lento, no repetible y fallaría sin internet — rompe tres de las seis reglas del ejercicio 1. La solución es reemplazar esa dependencia. Eso es exactamente lo que vienen a resolver los spies, stubs y mocks de los tres ejercicios siguientes.

Mini-reto

  1. Agrega a TarjetaTicket.vue un <slot name="acciones" /> al final del artículo.
  2. Escribe un test que monte la tarjeta pasándole ese slot: mount(TarjetaTicket, { props: {...}, slots: { acciones: '<button>Derivar</button>' } }).

Qué te tiene que quedar claro

  • mount ejecuta el ciclo de vida completo, incluido onMounted.
  • get para lo que debe existir, find().exists() para lo que no.
  • Todo lo que cambia estado se espera con await.
  • emitted() es el registro de eventos: no necesitas un espía para ellos.
  • Busca por data-test, no por clases de estilo.

Spies: mirar sin intervenir

Objetivo: registrar cómo se usó una función sin cambiar lo que hace. · 30 minutos · vi.fn() y vi.spyOn().

La definición en una frase.

Un spy es una función que anota cada vez que la llaman: cuántas veces, con qué argumentos, qué devolvió. Y nada más. El comportamiento original se mantiene intacto. El espía observa; no interviene.

Sirve para responder una pregunta muy concreta: «¿mi unidad llamó a esta colaboradora, y la llamó bien?» — cuando el efecto de esa llamada no se ve en la pantalla.

Leer el registro a mano

tests/componentes/ListaDeTickets.test.js — inspección detallada 
  it('permite revisar el registro de llamadas en detalle', async () => {
    const espia = vi.spyOn(auditoria, 'registrar')
    const wrapper = mount(ListaDeTickets, { props: { tickets: TICKETS } })

    await wrapper.get('[data-test="resolver"]').trigger('click')

    // mock.calls es un arreglo de arreglos: una entrada por llamada,
    // y dentro, los argumentos de esa llamada.
    expect(espia.mock.calls).toEqual([
      ['ticket_resuelto', { id: 3 }]
    ])

    // Útil cuando solo te interesa una parte del argumento
    expect(espia.mock.calls[0][1].id).toBe(3)

    // La última llamada, sin contar cuántas hubo
    expect(espia.mock.lastCall).toEqual(['ticket_resuelto', { id: 3 }])

    // Qué devolvió: { type: 'return', value: undefined }
    expect(espia.mock.results[0].type).toBe('return')
  })
Cuándo bajar a mock.calls.

Cuando el argumento es un objeto grande y solo te importan dos campos. En vez de escribir el objeto completo en toHaveBeenCalledWith —que te obliga a mantenerlo cada vez que alguien agrega un campo—, verificas solo lo que de verdad es parte del contrato. La otra opción elegante es expect.objectContaining({ id: 3 }).

El momento en que un espía deja de ser espía

Del espía al stub, en una línea 
// ESPÍA: mira y deja pasar. console.warn sigue ensuciando la salida del test.
const aviso = vi.spyOn(console, 'warn')

// STUB: mira Y reemplaza. El warn real ya no se ejecuta: la salida queda limpia.
const avisoSilenciado = vi.spyOn(console, 'warn').mockImplementation(() => {})

// Y con esto ya puedes comprobar el aviso sin llenar la consola de ruido:
expect(avisoSilenciado).toHaveBeenCalledWith(
  expect.stringContaining('prioridad desconocida')
)
Ésa es toda la diferencia entre un spy y un stub, y es la parte que la lección explica de forma enredada. Con Sinon son dos funciones distintas (sinon.spy y sinon.stub). Con Vitest es la misma herramienta: si le encadenas un .mockImplementation(), .mockReturnValue() o .mockResolvedValue(), pasó a ser un stub. Si no le encadenas nada, es un espía. Todo el ejercicio 5 vive de esa distinción.

Limpieza: el error que hace fallar el test de al lado

Un espía instalado sobre auditoria.registrar sigue instalado cuando termina el test. El siguiente test hereda el registro de llamadas del anterior y de pronto toHaveBeenCalledTimes(1) falla diciendo que hubo tres. Hay tres formas de limpiar y hacen cosas distintas.

vi.clearAllMocks()SíNoNo

Solo revierte lo que instalaste con vi.spyOn, porque solo ahí existe un original que devolver. Qué te tiene que quedar claro

  • Un spy observa sin cambiar nada; el original se sigue ejecutando.

  • clear borra historial, reset borra implementación, restore devuelve el original.
  • En cuanto le encadenas .mockImplementation(), ya no es un spy: es un stub.

Stubs: fijar la respuesta

Objetivo: reemplazar el comportamiento de una dependencia para forzar la situación que quieres probar. · 35 minutos.

Atención: en Vue, la palabra «stub» significa DOS cosas distintas.

Ésta es la confusión número uno de la lección y hay que resolverla antes de escribir una línea.

  1. Stub de función (el de Sinon, el de Vitest): reemplazas qué devuelve una función. Herramienta: vi.fn() con .mockReturnValue() y compañía.
  2. Stub de componente (el de @vue/test-utils): reemplazas un componente hijo por un marcador vacío. Herramienta: la opción global.stubs de mount.

Son ideas distintas con el mismo nombre. Vemos las dos, en ese orden.

Parte 1 — Stub de función: la definición

Un stub es un spy al que además le dictas la respuesta.

Lo dice la propia lección: «los Stubs son funciones Spy con comportamientos pre-programados […] una llamada a un Stub no ejecutará la función original». Se usa —y cito la lámina— «cuando se desea controlar el comportamiento de un test para forzar una situación, o cuando se desea evitar que un método específico sea llamado porque produce un efecto no deseado».

Traducido: lo usas cuando la dependencia es lenta, impredecible o tiene consecuencias — una petición HTTP, un pago, un correo, un archivo escrito en disco.

Las cinco formas de dictar la respuesta

Catálogo de stubs de función 
const obtenerTickets = vi.fn()

// 1. Un valor fijo, siempre el mismo
obtenerTickets.mockReturnValue([{ id: 1 }])

// 2. Una promesa que se resuelve — el caso más común con APIs
obtenerTickets.mockResolvedValue([{ id: 1, titulo: 'Impresora' }])

// 3. Una promesa que se rechaza — para probar el camino de error
obtenerTickets.mockRejectedValue(new Error('Servicio no disponible'))

// 4. Una implementación completa: puedes decidir según los argumentos
obtenerTickets.mockImplementation((estado) =>
  estado === 'abierto' ? [{ id: 1 }] : []
)

// 5. Un valor SOLO para la próxima llamada; después vuelve al comportamiento base
obtenerTickets
  .mockResolvedValueOnce([])            // 1ª llamada: la cola llega vacía
  .mockResolvedValueOnce([{ id: 9 }])   // 2ª llamada: ya hay un ticket
  .mockResolvedValue([{ id: 9 }, { id: 10 }])   // de la 3ª en adelante
El punto 5 es el que hace posible testear un reintento. «La primera vez falla, la segunda funciona» es un requisito real y muy difícil de reproducir contra un servidor de verdad. Con ...Once() son dos líneas.

Mocks: sustituir el módulo entero

Objetivo: reemplazar una dependencia completa y verificar cómo la usó tu unidad. · 35 minutos · vi.mock, vi.hoisted, temporizadores falsos.

Qué es un mock, según la lección.

Cito la lámina 24: «un Mock es una función sustituta como los Spies y Stubs, pero que además de ofrecer comportamientos preprogramados como los Stubs, ofrece expectativas preprogramadas. El Mock actuará como un sustituto del objeto completo».

Dos ideas ahí: sustituye todo el objeto o módulo (no una función suelta), y trae expectativas sobre cómo debe usarse. En Vitest la primera parte la hace vi.mock(); la segunda, las aserciones normales sobre el doble.

La diferencia de orden que confunde a todo el mundo

Sinon — expectativa ANTES 
const authMock = sinon.mock(Auth)

// Declaro lo que DEBE pasar…
authMock.expects("login")
  .once()
  .withArgs("usuario1@misitio.com", "123password")

/* … ejecuto el login … */

// … y recién acá se comprueba
authMock.verify()
authMock.restore()
Vitest — aserción DESPUÉS 
vi.mock('@/servicios/auth.js', () => ({
  login: vi.fn()
}))

/* … ejecuto el login … */

// Compruebo lo que pasó, con los mismos matchers
// que ya conoces del ejercicio 4

expect(login).toHaveBeenCalledWith(
  'usuario1@misitio.com',
  '123password'
)
Misma intención, momento distinto.

Sinon declara la expectativa antes y la verifica al final con verify(). Vitest deja que la cosa ocurra y después la interroga. La segunda forma es la que ya usaste con los spies — es una sola gramática para todo, y por eso la lección advierte: «se recomienda utilizar Stubs y Spies siempre que sea posible» y «no debería existir más de un Mock en un test». Ese consejo nace de lo frágil que es el estilo de expectativas previas.

El hoisting de vi.mock: el error nº 2 de la unidad

Vitest sube todas las llamadas a vi.mock al inicio del archivo, antes de cualquier import. Tiene que hacerlo: si no, el módulo real ya estaría cargado cuando llegas a falsificarlo. La consecuencia práctica es contraintuitiva.

Lo que uno escribe por instinto

// cuando `respuesta` todavía no existe.

const { respuesta } = vi.hoisted(() => ({
  respuesta: [{ id: 1 }]

  obtenerTickets: vi.fn(() => respuesta)

Y por lo mismo: vi.mock va SIEMPRE en el nivel superior del archivo.

Nunca dentro de un describe, de un it o de un beforeEach. Si lo pones adentro, se sube igual y el resultado es que afecta a todo el archivo, no solo a ese bloque — que casi nunca es lo que querías.

Trampa fina: flushPromises() con temporizadores falsos se cuelga.

flushPromises se apoya en un setTimeout, y si congelaste el reloj ese temporizador nunca se dispara: el test se queda esperando hasta el timeout de Vitest y falla con un mensaje que no dice nada útil.

Regla práctica: activa vi.useFakeTimers() DESPUÉS del montaje y del flushPromises inicial, justo antes de la parte que necesita controlar el tiempo. En la integradora hay un ejemplo exacto de esto.

Cómo elegir, en tres preguntas.
  1. ¿Necesito que la función original siga funcionando y solo quiero mirar? → spy.
  2. ¿Necesito controlar la respuesta de una función suelta? → stub.
  3. ¿La dependencia es un módulo entero que ni siquiera debe cargarse (axios, el router, un SDK)? → mock.

Qué te tiene que quedar claro

  • vi.mock sustituye un módulo completo; el stub, una función.
  • vi.mock se sube al inicio del archivo: por eso existe vi.hoisted.
  • La expectativa previa de Sinon se convierte en una aserción posterior con Vitest.
  • Se mockean las fronteras (red, router, reloj, navegador), no tu propia lógica.
  • flushPromises y los temporizadores falsos no se llevan bien: cuida el orden.
  • Spy → observo. Stub → dicto la respuesta. Mock → reemplazo el módulo y hago las dos cosas.

import { computed, onMounted, ref, watch } from 'vue'
import { useRouter } from 'vue-router'
import { obtenerTickets, resolverTicket } from '@/servicios/ticketsApi.js'
import { auditoria } from '@/servicios/auditoria.js'
import GraficoDeCarga from './GraficoDeCarga.vue'
import ListaDeTickets from './ListaDeTickets.vue'

const tickets = ref([])
const cargando = ref(false)
const error = ref('')
const filtro = ref('')

let temporizador
const router = useRouter()

const visibles = computed(() =>
  tickets.value.filter(t =>
    t.titulo.toLowerCase().includes(filtro.value.toLowerCase())
  )
)

const serie = computed(() => visibles.value.map(t => t.minutosAbierto))

async function cargar() {
  cargando.value = true
  error.value = ''
  try {
    tickets.value = await obtenerTickets('abierto')
  } catch {
    error.value = 'No pudimos cargar la cola de tickets. Intenta nuevamente en unos segundos.'
  } finally {
    cargando.value = false
  }
}

async function resolver(id) {
  await resolverTicket(id)
  auditoria.registrar('ticket_resuelto', { id })
  tickets.value = tickets.value.filter(t => t.id !== id)

  // Si vaciamos la cola, el panel deja de tener sentido: al tablero
  if (tickets.value.length === 0) router.push('/cola-vacia')
}

// El borrador del filtro se guarda con retardo: escribir en localStorage
// en cada tecla es caro y no aporta nada.
watch(filtro, (valor) => {
  clearTimeout(temporizador)
  temporizador = setTimeout(() => {
    localStorage.setItem('filtro-panel', valor)
  }, 800)
})

onMounted(cargar)
</script>

La regla de oro, en una frase

Prueba el comportamiento observable, no la implementación.

Si tu test se rompe cuando alguien renombra una variable interna o cambia un computed por un method, no estabas probando el componente: estabas probando cómo está escrito. Un buen test sobrevive al refactor y solo falla cuando cambia lo que el usuario ve o lo que el componente promete.

Checklist antes de dar un test por terminado

Repásalo con cada test que escribas

  • El nombre dice qué hace y cuándo, sin abrir el código.
  • Prueba una sola cosa: si falla, sé exactamente qué se rompió.
  • Corre solo, con it.only, y pasa igual.
  • Corre mil veces y da siempre el mismo resultado.
  • No toca la red, ni el reloj real, ni el localStorage de otro test.
  • Cubre el camino feliz y el error y el vacío.
  • Usa el doble más liviano que sirva: antes spy que stub, antes stub que mock.
  • Si tuve que mockear media aplicación, la unidad está haciendo demasiado.

Lo que sigue

Pruebas end-to-end.

La segunda mitad de la presentación son Cypress y Nightwatch: probar el sistema completo en un navegador real, con el servidor levantado y sin un solo doble. Es el complemento natural de lo de hoy, no su reemplazo.

La proporción sana: muchas pruebas unitarias, algunas de integración, pocas end-to-end. Las unitarias te dicen qué se rompió en milisegundos; las e2e te dicen que el sistema completo funciona, pero tardan minutos y fallan por razones que nada tienen que ver con tu código. Si inviertes al revés, vas a tener una suite lenta en la que nadie confía.

Lo que se llevan de hoy.

Tres palabras que la mayoría usa como sinónimos y que ahora saben distinguir: spy observa, stub responde, mock reemplaza. Y un criterio para elegir: el doble más liviano que resuelva el problema.

Lo difícil de testear nunca fue la sintaxis. Es decidir qué vale la pena probar y dónde poner la frontera entre tu unidad y el mundo. Eso se aprende escribiendo tests que después hay que mantener.
